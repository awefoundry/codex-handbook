# Codex 提示词怎么写：目标、上下文、边界和验收四件事，附官方 9 个编程任务示例

> 本文在线版：[codexguide.io/guides/codex-prompting-guide](https://codexguide.io/guides/codex-prompting-guide)

> 核对依据：官方 [Prompting](https://learn.chatgpt.com/docs/prompting)（2026-11-12 核对）。文中的提示词示例按官方英文示例意译成中文，结构和要点不变；官方原文可以在上面的页面查到。

很多人刚用 Codex 时会去找「万能提示词模板」。官方的说法很直接：**不需要技术语法，也不需要固定公式**，用自己的话开头，看结果，再用后续消息调整。

但「随便写」和「写清楚」差别很大。同样是修 bug，「设置页保存有问题」和「按这 5 步能复现、不许改 API、修完重新复现并跑测试」，拿到的结果完全不一样。这篇把官方文档里的方法和 9 个编程示例整理成能直接套用的写法。

## 先看结论

- **短提示词往往就够**。任务大或重要时，再补齐这几部分：
  - 目标：要它做什么；
  - 上下文：哪些信息有帮助；
  - 输出：格式、长度、详细程度；
  - 边界：什么不能动，什么要先问你。
- **写 Codex 提示词，官方给的四个要点**：
  - 说清楚你要的**行为**；
  - 指出相关的**代码或复现步骤**；
  - 保留重要的**约束**；
  - 说明**怎么验证**改动。
- **先说结果，不必列步骤**。只有流程本身重要时才描述流程。
- **边界只写一两条最要紧的**，不用控制每一步。
- **多步任务先 `/plan`**，确认方案再动手。
- **运行中可以插话**：Steer 加到当前轮，Queue 留到下一轮。

## 一条 Codex 提示词的四个部分

把官方「Prompting Codex」一节的要求拆开，就是下面四件事。

| 部分 | 写什么 | 例子 |
|---|---|---|
| 目标 | 你要的行为或结果，不是步骤清单 | 「点保存后设置要真的写进去，刷新不丢」 |
| 上下文 | 相关文件、复现步骤、报错、截图 | `@settings.ts`、5 步复现、终端报错原文 |
| 边界 | 不能改的东西、要先确认的动作 | 「不要改 API 结构」「改动尽量小」 |
| 验收 | 怎么证明做对了 | 「修完重新复现；跑 lint 和最小相关测试；报告命令和结果」 |

几个细节：

- **上下文要精，不要多**。官方建议只给可能改变结果的信息，并说明每份材料要它看什么。
- **IDE 扩展会自动带上你打开的文件**；CLI 里要明确写路径，或者用 `/mention` 和 `@` 补全路径来附加文件。
- **截图只给视觉要求**。框架、路由、组件风格这些实现约束要另外写；悬停状态、校验规则、键盘交互这类截图里看不出来的行为，也要用文字补上。
- **边界写「会造成真问题」的那几条**。比如「不要改已批准的接口」「只用我给的资料，缺信息就标出来，不要猜」。

## 官方 9 个编程任务示例

官方文档按「什么时候用、用哪个入口、步骤、Codex 自动能看到什么、怎么验证」列了 9 个工作流。下面是每个示例的核心提示词（中文意译）和验证方式。

### 1. 读懂一段代码

适合接手服务、新人上手、理解协议或请求流程。IDE 里先打开相关文件，选中关心的代码：

```text
解释请求是怎样流经选中代码的。

包括：
- 涉及的每个模块各自负责什么（简短）
- 在哪里校验了哪些数据
- 改这段代码时要注意的一两个坑
```

**验证**：让它给一个你能核对的清单，比如「把请求流程写成编号步骤，再列出涉及的文件」。CLI 里可以用 `@foo.ts @schema.ts` 直接点名文件。

### 2. 修一个能复现的 bug

官方推荐在仓库根目录启动 CLI，给复现步骤和怀疑的文件：

```text
Bug：在设置页点「保存」，有时显示「已保存」但改动没有保存下来。

复现：
1) 启动应用：npm run dev
2) 打开 /settings
3) 切换「Enable alerts」
4) 点保存
5) 刷新页面：开关恢复原样

约束：
- 不要改 API 结构。
- 修复尽量小，可行的话补一个回归测试。

先在本地复现这个 bug，再给出补丁并运行检查。
```

官方特别说明：**你提供的复现步骤和约束，比一句高层描述更重要**；命令输出、调用点、堆栈这些由 Codex 自己去找。

**验证**：要求它修完重新跑复现步骤；有固定检查流程的话补一句「修完运行 lint 和最小相关测试，报告命令和结果」。

### 3. 写测试

IDE 里选中函数所在的行，用命令面板的「Add to Codex Thread」加入上下文：

```text
为这个函数写单元测试，遵循项目里其他测试的写法。
```

CLI 里直接点名函数和文件：「给 `@transform.ts` 里的 `invert_list` 函数加测试，覆盖正常路径和边界情况。」

### 4. 照着截图做原型

把截图存到本地（比如 `./specs/ui.png`），拖进终端附加到提示词，然后补上约束和产出：

```text
根据这张图做一个新的仪表盘。

约束：
- 用 react、vite 和 tailwind，代码用 typescript。
- 间距、字体和布局尽量贴近原图。

产出：
- 一个渲染这个界面的新路由或页面
- 需要的小组件
- README.md，写清本地怎么运行
```

**验证**：让它启动开发服务器（如果允许），并告诉你到哪个地址、哪个路由看效果。

### 5. 边看边调 UI

在另一个终端开着 `npm run dev`，用小而具体的提示词一轮轮改：

```text
选方案 2。

只改页头：
- 字体更有编辑感
- 留白加大
- 确保手机上也好看
```

**验证**：在浏览器里看实时效果，喜欢的改动提交，不喜欢的撤回。**你撤回或手改过的地方要告诉 Codex**，免得它下一轮又改回去。

### 6. 本地出方案，交给云端重构

先确保当前工作已提交或 stash，方便对比。让 Codex 出重构计划（有 `$plan` Skill 时可以显式调用），写清目标和约束：

```text
我们要重构认证子系统：
- 拆分职责（token 解析、会话加载、权限）
- 减少循环引用
- 提高可测试性

约束：
- 用户可见的行为不变
- 公开 API 保持稳定
- 给出分步迁移计划
```

再要求它修改计划，比如「写明每个里程碑移动哪些文件」「加上回滚方案」。确认后在 IDE 输入框下方选择云端环境，发出「实现计划里的第 1 个里程碑」，Codex 会带着当前对话上下文（包括计划和本地改动）在云端新开对话。官方提醒：云端任务在隔离环境里运行，除非为环境开启联网，否则 agent 阶段不能上网。

### 7. 提交前本地审查

在 CLI 里运行 `/review`，可以加关注点：

```text
/review Focus on edge cases and security issues
```

**验证**：根据反馈修完，再跑一次 `/review` 确认问题已解决。

### 8. 审查 GitHub PR

先在仓库开启 Codex Code review，然后在 PR 里评论 `@codex review`，也可以写明重点，比如 `@codex review for security vulnerabilities and security concerns`。

### 9. 改文档

在 IDE 打开要改的文档，或在 CLI 用 `@` 点名，然后写清范围和验证要求：

```text
更新「advanced features」文档，加入认证问题排查指引。检查所有链接都有效。
```

**验证**：看渲染后的页面。

## 多步任务：先 /plan，再 /goal

官方建议：多步任务在应用输入框里先输入 `/plan`，让 Codex 调查并提出方案，确认后再动手。Goal 模式可用时，可以在计划之后用 `/goal` 设定一个持续目标。

Plan 模式的用法见 [Codex Plan 模式](./08-Codex-Plan模式-先出计划再动手.md)。

## 运行中插话和排队：Steer 与 Queue

Codex 正在工作时，不用等它跑完也能发消息：

- **Steer（插话）**：消息加到当前这一轮，用来改方向、补漏掉的细节或给新信息；
- **Queue（排队）**：消息留到下一轮，用于应该等当前工作结束再做的后续任务。

怎么操作：

- **Codex CLI**：运行中按 <kbd>Enter</kbd> 是插话，按 <kbd>Tab</kbd> 是排队；
- **桌面应用**：在 **Settings > General > Follow-up behavior** 里选默认行为。排队的消息显示在输入框上方，可以编辑、调整顺序、发送或删除；设置项里也写了临时切换成另一种行为的快捷键。

## 常见写法问题

| 写法 | 问题 | 改成 |
|---|---|---|
| 「优化一下这个页面」 | 没有目标，也没有验收标准 | 「首屏加载从 X 秒降下来；只改图片加载和打包配置；改完用同样方式测一次，报告前后数据」 |
| 一次贴十几个文件 | 上下文太多，重点被淹没 | 只给入口文件和最可疑的一两个文件，其他让 Codex 自己找 |
| 把每一步都规定死 | 限制 Codex 搜索和比较 | 先说结果，只有流程本身重要时才写流程 |
| 没写「不能动什么」 | 顺手改了 API、依赖或配置 | 加一两条最要紧的边界 |
| 「做完告诉我」 | 不知道它做对没有 | 要求报告跑了哪些命令、结果是什么、还有什么没验证 |

## 每次都要说的话，写进 AGENTS.md

如果你发现每条提示词都在重复「用 pnpm」「改完跑 `pnpm test`」「不要动 migrations 目录」，就该把它们写进项目的 `AGENTS.md`。提示词只放这一次任务的目标、上下文、边界和验收，长期规则交给 AGENTS.md，见 [AGENTS.md 怎么写](../10-配置模型与权限安全/07-AGENTS.md怎么写-项目规则继承关系与验收标准.md)。

对话太长、上下文开始混乱时，什么时候压缩、什么时候新开会话，可以看 [Codex 上下文窗口与压缩](./07-Codex上下文窗口与压缩-compact自动压缩与何时新开会话.md)。
