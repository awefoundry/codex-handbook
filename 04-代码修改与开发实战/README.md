# 代码修改与开发实战

围绕日常开发任务，展示 Codex 如何修改真实项目，以及人应该检查什么。

## 内容范围

- 增加一个小功能。
- 修复可以复现的 Bug。
- 修改多个相互关联的文件。
- 安装或升级依赖。
- 小范围重构和补充文档。
- 控制修改范围，避免不必要的重写。

实操文章需要提供修改前状态、操作过程、代码差异和验证结果。

## 本节定位

03 节解决“应该改哪里、影响什么”；本节解决“已经知道改哪里之后，怎样让 Codex 完成一组可控的代码变更”。重点不是展示一段看起来能运行的代码，而是让读者学会把改动限制在明确范围内，持续检查差异，并在必要时停下来重新规划。

本节默认读者已经会：

- 从需求或报错定位入口、关键文件和影响范围。
- 给 Codex 写出目标、范围和验收标准。
- 在本地运行项目的基本命令。

## 对标后的主线

对照 OpenAI Codex、Claude Code、Cursor、GitHub Copilot coding agent 和 Aider 的官方文档，可以看到它们在“代码修改”部分反复强调同一条闭环：

> 读取上下文 → 先计划 → 定向编辑 → 运行最小验证 → 检查 diff → 再决定是否扩大范围。

差异主要在产品形态：Codex 和 Claude Code 强调终端中的完整工作循环与计划/权限边界，Cursor 强调 Agent 跨文件编辑，Copilot coding agent 强调从 Issue 到分支和 PR，Aider 强调 Git 仓库内的增量编辑、自动测试和撤销。因此本节不按产品按钮罗列功能，而按开发者真实遇到的改动类型组织内容。

## 阅读顺序

建议先完成 01～04，建立“计划、实现、收敛、验证”的基本手感；再根据工作类型阅读 05～10；最后用 11～12 处理批量化和自动化场景。

### 建议分成三段学习

- **建立闭环（01～04）**：从计划到小功能和 Bug 修复，先学会控制单次改动。
- **处理复杂变更（05～09）**：跨文件、前端视觉、依赖、重构和高风险文件。
- **扩大规模（10～12）**：批量迁移、失控收敛和非交互自动化。

- 分支、提交、冲突、PR 和正式 Review 放在 [05-Git协作与代码审查](../05-Git协作与代码审查/)。本节可以使用 `git diff` 观察范围，但不把 Git 协作写成主教程。
- 测试设计、日志排查、浏览器开发者工具和最终质量验收放在 [06-测试调试与质量保障](../06-测试调试与质量保障/)。本节只展示完成改动所需的最小验证，并链接到后续深入内容。
- Skills、插件、MCP、模型选择、权限配置和多 Agent 编排分别放在 07～11 节。本节可以说明“这里调用了什么能力”，但不展开配置教程。
- 多文件综合项目和完整产品任务放在 [14-真实案例复盘](../14-真实案例复盘/)。本节的示例应保持单一主线，避免变成没有边界的长案例。

## 每篇文章的最低结构

1. 说明任务背景、读者已有前置知识和本次明确不做什么。
2. 给出修改前状态、入口文件、运行前提和可复现输入。
3. 展示给 Codex 的任务、计划和批准/调整过程。
4. 按小步提交代码修改，解释每一步为什么没有扩大范围。
5. 展示关键 diff、最小验证结果和仍需人工确认的事项。
6. 记录失败尝试、回滚方式、常见误区和下一篇的衔接。

每篇至少保留一份真实的前后对照：代码 diff、命令输出、截图或文件清单。没有实际执行过的命令和版本行为标记为“待验证”，不要把模型推测写成产品保证。

## 首批写作建议

如果不准备一次性写完 12 篇，先写 01、03、04、05、08、11 六篇。这六篇覆盖最常见的“加功能、修 Bug、跨文件、重构、发现失控后收敛”场景，也最容易与 03、05、06 三个相邻栏目形成清晰的前后链接。
