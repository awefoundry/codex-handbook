# Codex 自动排查性能回归：拆解 OpenAI 的 Performance Factory，把排查流程写成 Skill、告警自动开任务、部署后再复核

> 核对依据：OpenAI 官方博客 [How OpenAI’s Performance Factory keeps ChatGPT fast](https://openai.com/index/how-openai-performance-factory-keeps-chatgpt-fast/)（2026 年 11 月 19 日，作者 Okay Zed、Cyrus Forbes）。2026-11-20 再次打开该页，正文与下面引用的阶段、组件和数字一致。博客配图没有放进本仓库，需要看图时打开原文。Hacker News 讨论 [item 50563482](https://news.ycombinator.com/item?id=50563482) 同一天打开为 8 分、1 条评论。`perf-forensics` 和 Performance Factory 都没有公开下载。本文没有 OpenAI 的内部指标、告警或云端环境，没有跑过这套流程。

这篇给已经会用 Codex、想把「服务变慢了怎么查」做成可重复步骤的人。Skill 的文件格式见 [从零创建 Codex Skill](../07-Skills实战/04-从零创建Codex-Skill.md)。云端环境怎么发布见 [Codex Cloud 云端环境](../12-官方工具与集成/12-Codex-Cloud云端环境-创建发布环境-联网与密钥设置.md)。把线上错误 Issue 接进来是另一件事，见 [连接 Sentry](../12-官方工具与集成/04-Codex连接Sentry排查线上错误.md)。

## 先说结论

OpenAI 的顺序不是先造一个自动改生产的系统。博客把过程写成六步，真正让代理能独立做完一次排查的，是中间那份共享 Skill。

普通团队可以照做的部分也停在这里：把你们已经在用的排查角度写成 `SKILL.md`，用过去真实发生过的回归看它会不会把时间和影响范围说对，再决定要不要让告警去开一条 Codex 任务。合并、部署和架构取舍仍要留给工程师。

OpenAI 的 `perf-forensics` 和 Performance Factory 没有公开。下文凡是出现代码块的地方，都是本站按博客里的三个排查角度写的示例，不是他们的内部文件。

## OpenAI 走过的六步

博客用六步描述性能团队怎么从人工排查走到工厂。原文的顺序是：

1. **Codex 之前。** 工程师自己看指标和日志、比较 trace、在线上机器上调试、读代码。同类问题反复出现时，他们做了更专门的工具，例子是 CPU profiler 和 allocation profiler。时间长了，这类性能工具积累了 30 多个。
2. **Codex 当搭档。** 工程师可以问「为什么变慢了」。Codex 能搜代码、找相关的指标和 trace、顺着服务之间的调用往下看，并做合适的 profiling。人仍然要掌握该用哪个工具、调查往哪边带。
3. **可复用的 Skill。** 他们把性能团队的排查过程写成共享 Skill，名叫 `perf-forensics`。它告诉 Codex 有哪些工具、什么时候用、一次变慢要沿哪几个角度查。他们用过去的回归做成 evals，反复改这份 Skill。对博客点名的那类问题（例如 ChatGPT 的延迟和可用性下降），可以把一条告警交给 Codex，一次运行拿回诊断，不用人逐步带着走。
4. **人当中转。** Skill 变多之后，告警响了，工程师要做的往往只是把告警贴进 Codex、选对 Skill，再把结论贴回 Slack。
5. **自动排查。** 调查改到云端，告警可以自己开一条 Codex 会话。Codex 把结论发回 Slack 线程。到此为止：人还得拿起诊断、写修复、部署后再看有没有用。告警一多，连「哪几条值得看」都要在 Slack 里翻。
6. **工厂。** Performance Factory 跟踪每条未完成任务的下一步，到了该做的步骤就派一个代理。任务自己保存状态和发现，所以工作和结论可以在代理和工程师之间交接，代码评审或部署之后还能接着做。一条回归从调查告警开始，到在生产环境确认恢复结束。

博客把这六步写成服务团队可以借鉴的过程，不是一份安装手册。

`perf-forensics` 让 Codex 从三个角度查一次变慢。原文是：

- 找出变慢是什么时候开始的
- 找出受影响的是哪些请求
- 调查部署或配置变更能不能解释这次变慢

这三个角度是后文示例 Skill 仅有的调查步骤。博客没有列出那 30 多个工具的名字，本文也不编。

## Performance Factory 的四个组件

博客写系统由四部分组成：带可配置工作流的任务服务、把就绪工作派给代理的循环、在云端跑 Codex 的 API，以及在事情变化时叫醒代理的订阅（例如 GitHub 上出现评审评论，或一次部署完成）。

| 组件 | 博客里的职责 |
| --- | --- |
| 任务服务 | 工程师用配置文件和 Markdown 提示词定义工作流。配置列出任务能经过的状态、允许的转移，以及哪些步骤必须由工程师做。每一步的提示词分开写。所有工作流在一个界面里可见，工程师可以看进度，也可以把任务分给更有上下文的同事。 |
| 派发循环 | 定期查看哪些任务可以进入下一步。对每个就绪任务，用该状态对应的说明发起一轮 Codex。代理把进展写回任务，这一步做完就把它挪到下一状态。 |
| 云端 Codex | OpenAI 做了一个内部 API，用来在云端发起一轮 Codex。这一轮跑在他们网络内的环境里，能访问代码仓库，以及工程师用的可观测工具：指标、日志、trace、CPU profile 和内存快照。代理使用服务身份，便于限制权限，也便于分清哪些动作来自性能代理。 |
| 订阅 | 任务如果要等人或等部署，不必一直占着代理。它可以订阅 pull request 上的评审评论或失败的 CI。事件对上之后，任务重新变为就绪，派发循环再派代理继续。 |

博客给了一个代码变更任务的目录形状：`code-change/config.toml`，以及 `code-change/work/` 下的 `implementing.md` 和 `reviewing.md`。这是在说明「状态机用配置，每一步用一篇 Markdown」。它不是可以克隆的仓库，本文没有这些文件。

云端环境、联网和密钥如果要用 Codex Cloud 的公开产品来做，按 [云端环境一文](../12-官方工具与集成/12-Codex-Cloud云端环境-创建发布环境-联网与密钥设置.md) 的官方文档来，不要把博客里的内部 API 当成 `codex cloud` 的参数。

## Regression Workflow 怎么跑

博客说，找到根因并修掉回归，是 Performance Factory 里的第一条工作流，名叫 Regression Workflow。一条性能回归要经过的阶段包括：需要调查、已找到根因、已提出修复、已解决。自动工作流按同样的阶段推动任务。

配置过的性能告警一响，工作流就开一条任务。任务把状态和关键发现记在任何一个代理的上下文之外，别的代理或工程师都能接上。工程师可以在 Slack 或这个工作流的界面里跟进、补充上下文、审查改动。修复部署之后，一个代理检查性能有没有回到原来的基线，然后再把任务标成解决。

博客图示里的步骤是：检测到回归，代理找根因，代理提出修复，工程师审查并部署，代理核对是否恢复，然后解决。若仍然回归，就回到调查。

调查的第一段，博客写得更具体：代理先看哪些指标变差、什么时候开始变、哪些服务请求受影响。告警往往是指标越过阈值才响，回归本身可能早几个小时就开始了。代理要往回看，找到指标第一次变差的时间。然后比较一组一组的请求：是相似的请求真的变慢了，还是本来就慢的请求变多了。这两种发现指向不同的原因。时间和范围清楚之后，再看部署和 feature flag，读相关代码，核对变更是什么时候到达这些请求的，并用日志或 trace 检验这段代码能不能解释现象。

他们后来加了对抗式复核：另开一条 Codex 会话，专门尝试推翻刚才的诊断。复核会重查假设、检验反事实。博客举的例子是：如果一次发布导致变慢，那么没有碰到这次发布的相似请求是否仍然正常；如果把可疑变更回滚，相关指标是否恢复。

博客里的一个实例是：代理把失败的 ChatGPT 对话追溯到图片下载错误，并标成原因已找到。复核的 Codex 注意到，负责定位文件的内部服务已经恢复，图片请求却还在失败。这个诊断解释不了持续的失败，于是复核把调查重新打开，并记下还需要确认什么。

他们还写了一次人工抽查：100 条根因建议里，70% 被评为准确，30% 需要再细化，或没有完全建立因果关系。工作流里用不同的轮次分别做调查、质疑诊断和提出修复。

诊断通过对抗式复核之后，工作流让 Codex 实现修复并打开 pull request。工程师审查，决定是否合并。每条任务有一份报告，自动生成回归摘要、影响、根因和拟议修复；他们把摘要调到便于扫读，并放上指标时间序列、CPU 火焰图和 trace。工程师可以直接改 PR，也可以按诊断自己写修复。PR 上留下评论时，工作流会叫醒代理去处理。

部署之后的核对有三种结果，都按博客原文：

- 性能回到原先基线：代理把任务标成已解决。
- 只恢复了一部分：代理把原来的回归标成解决，并为剩下的变慢另开一条任务。剩下的部分可能是另一个原因。
- 没有改善：代理记下发生了什么，把回归送回调查。

博客明确写，把修复做对比找到原因更难。他们见过代理提出的改动比需要的更复杂，或引入新问题。因此拟议修复也有一轮对抗式复核，检查它是否对着根因，并尽量抓住缺陷或意外后果。有些修复需要更高一层的架构决定。博客的例子是：加缓存可能更快，但会带来过期数据。这类改动需要了解服务的工程师来权衡。

他们还在用「代理提出的修复」和「工程师最终合并的改动」做对照，用来看提案差在哪里，并改进工作流。用合成性能测试让代理在请人审查之前自己量一遍修复，以及让代理识别低风险改动并最终在没有人的情况下合并，博客写的是正在做和正在探索，不是已经交付的开关。

官方数字集中在这一段，查询日期 2026-11-20，均来自这篇博客，不是本站测量：

| 博客原文 | 范围 |
| --- | --- |
| 三个多月 | Regression Workflow 的统计区间 |
| 1,700 多次排查 | 该工作流跟踪到的调查次数 |
| 600 多个根因 | 在这些调查里找到根因的案例数 |
| 每天 17 次 | 博客写 “That’s 17 automated investigations every day” |
| 30 多个性能工具 | Codex 之前，团队积累的性能工具数量 |
| 100 条里 70% 准确 | 对根因建议的一次人工复核；另外 30% 需要再细化或没有完全建立因果关系 |

## 普通团队照着做

下面这份 Skill 是**本站按文章思路写的示例模板，不是 OpenAI 的 `perf-forensics`**。它只用了博客里的三个排查角度，没有工具名，也没有指标名。你们自己的指标、日志和变更记录，写在步骤里你们已经在用的那些名字上。

文件可以放在个人目录 `~/.agents/skills/perf-regression-notes/SKILL.md`，或仓库的 `.agents/skills/perf-regression-notes/SKILL.md`。`name` 和 `description` 是官方 [Build skills](https://learn.chatgpt.com/docs/build-skills) 要求的两项。描述要写清什么时候用、什么时候不用。格式和触发方式见 [从零创建 Codex Skill](../07-Skills实战/04-从零创建Codex-Skill.md)。

```md
---
name: perf-regression-notes
description: 当用户给出一次性能变慢的告警或现象，并要求排查原因时使用。沿三个角度整理时间、受影响请求和能否用部署或配置变更解释。不用于在没有人审查时修改生产配置或合并代码。
---

# 性能变慢排查

这是一份排查记录模板。没有用户提供的指标、日志或变更记录时，不要编造数字和原因。

1. 找出变慢从什么时候开始。把用户给出的告警时间和你能看到的更早变化分开写。看不出起点就写「起点不明」。
2. 找出受影响的是哪些请求。区分「相似请求变慢了」和「本来就慢的请求变多了」。证据不够就写「范围不明」。
3. 调查部署或配置变更能不能解释这次变慢。只引用用户提供的变更。对得上就写对应关系；对不上就写「现有变更解释不了」，不要换一个看起来合理的原因收尾。
4. 输出三节：起点、影响范围、变更是否解释得了。每一节都写证据来自哪里，以及还缺什么。
5. 不要修改代码，不要开 pull request，除非用户在这次对话里明确要求，并且人会审查。
```

博客里 OpenAI 用历史回归做 evals 的方法，可以收成你们自己的检查，不必先有他们的工厂：

- 每条用例从一次过去的真实事故开始，只保留当时的告警，拿掉会直接说出答案的事后说明。
- 换一个新的会话来跑，不要带着上一回的记忆。
- 分开打分：问题什么时候开始、有多大、哪些请求受影响，是一组；它把原因排对了没有、还剩什么不确定，是另一组。时间对了仍可能怪错一次部署。
- 指标和 trace 会过期。一次测试有没有用，取决于你是否知道调查员当时能看到什么。

官方文档里的 Skill 作者建议是：一个 Skill 只做一件事，能用说明解决的先不要写脚本，步骤用祈使句并写清输入输出。上面的模板按这个边界写成只读记录。本文没有把这份文件装进 Codex，也没有用历史事故跑过它。

## 落地顺序与边界

按博客的六步，普通团队更稳的顺序是：

1. **人先能讲清步骤。** 把三个角度写成 Skill。第一次用时，由人把告警原文复制进 Codex，并点名这份 Skill。看它写出的起点、范围和「解释不了」是不是人能核对。
2. **用旧事故抽查。** 至少拿几条已经知道结论的回归，看它会不会在证据不够时仍写死一个原因。这一步没有通过，就不要接告警。
3. **再考虑少一次复制粘贴。** 告警要自动开任务时，可以用 [Codex Cloud](../12-官方工具与集成/12-Codex-Cloud云端环境-创建发布环境-联网与密钥设置.md) 的环境，或在已经有人看管的机器上用 `codex exec` 跑一段只读排查。无论哪一种，都先让它只写调查记录。
4. **修复和部署留人。** 博客把「审查并决定发布什么」放在工程师身上。加缓存这类会改变数据新鲜度的决定，不要交给只看过一份告警的会话。部署之后的复核是另一个步骤：回到基线、只恢复一部分、或没有改善，三种结果都要写下来，而不是只写「已修复」。

必须留给工程师的，博客已经点了名：合并与否、部署、以及需要权衡的架构改动。另外，代理的原始输出可能是一大段难读的文字。他们后来把相关事件归并、按团队关心的指标分组、按估计影响排序，是为了让人把注意力放在决定上。你们如果还没有这份给读者的摘要，自动化只会把更多调查堆到同一个人面前。

博客最后写，他们正在做没有告警也去找变慢和优化的做法，以及把已知模式（例如服务副本开得比需要的多）收成定期工作流。这些是 “what’s next”，不是 Regression Workflow 已经公开的配置。
