# gzhwz：公众号文章工作流

按固定顺序处理文章、配图和引流，交付可发布的正文、图片和待补信息清单。保留原稿与原图，不凭空补写事实、数字、引用、联系方式或链接。

## 执行顺序

### 0. 复用教程环境并记录实际处理工具
- 先查找文章对应的 `environment.md`。已有记录时复用，不把完整版本表复制进正文或交付报告；没有记录时只为本次实际使用且影响输出的工具建立内部记录。
- 开始前先盘点文章目录中已有的处理结果、备份目录、图片编号和报告文件。已有步骤已完成且验收通过时直接复用，不重复润色、图片处理、复制备份或生成相同链接。
- 同一篇文章只维护一个 `gzhwz-processing-report.md`（已有同名报告就更新，不另建平行报告）。该文件统一记录处理环境摘要、原图备份映射、图片处理映射、编号与验收、链接埋点、二维码验收和待确认项；`environment.md` 只保存完整工具证据，不重复记录图片或链接结果。
- 仅检测实际参与处理的运行时、库或程序，例如使用 Python 和 Pillow 处理图片时记录二者版本，使用 FFmpeg 或 ImageMagick 时才检测对应版本。不要例行检测或展示未使用的 Node、npm、Python、Shell、插件和技能版本。
- 只有当操作系统或 shell 会改变输出或复现方式时才记录它们。版本以实际检测结果为准，查不到时写明原因，不得推断。
- 将完整取值方法和证据写入文章工作区的 `environment.md`；若文章没有该工作区，则写入本轮备份目录中的 `processing-environment.md`。这些内部记录不得插入发布正文。
- 交付报告和最终回复只保留一行摘要并指向内部记录，例如：`处理环境：Windows 11 24H2；Python 3.13.5 + Pillow 12.3.0；2026-08-13 核验。完整记录：<path>`。
- 无关工具的版本未知不影响继续处理。只有实际处理工具不可用、导致操作无法执行或结果无法验收时才停止并报告。

### 1. 识别输入并保护原件
- 确认正文格式、图片目录、文件名、图片在正文中的出现顺序和交付目录。
- 图片编辑前检查是否已有完整、可打开且与当前原图一致的备份；已有有效备份时复用，不再次复制。没有有效备份时才创建 `<文章目录>/image-backup-YYYYMMDD-HHmm/`，并把“原图 -> 输出图”映射写入唯一的 `gzhwz-processing-report.md`。备份失败时停止图片编辑并报告原因。
- 先统计正文实际图片数量，再校对已有图片编号；未确认总数前不重编号。

### 2. 文章人性化润色
- 按 `humanize-zh-prose`、`human-writing`、`humanizer-zh` 的要求处理表达，必要时读取对应 `SKILL.md` 和 references。
- 保留作者立场、事实、数据、引用、专名、链接和目标文体；不编造细节，不把文章改成提纲，不用机械禁词清单替代语境判断。

#### AI 标题简洁规则

- AI 拟定或改写标题时，只保留文章的核心主题、对象、动作或结果；标题应简洁、清晰，读者无需阅读正文即可判断内容范围。
- 删除与主题无关的内部状态、流程提示和免责声明，例如“未核验”“没核验”“待确认”“待补充”“用户提供”“AI 生成”“处理记录”等；这些信息只能写入内部报告，不能进入发布标题、图注或正文导语。
- 不为追求完整而堆叠多个结论、平台名称、操作步骤或形容词；无法由原稿核验的事实不写进标题，改用更准确的概括或列入待确认项。

### 3. 配图：强制统一调用 imagegzh

本阶段必须使用 `$imagegzh` 规定的流程处理每一张正文配图；不能只在文字中“参考 imagegzh”，也不能用另一套图片样式替代。若当前运行环境未安装该 Skill，应先按仓库 `skills/README.md` 的说明配置，不能假设本机路径。

#### 正文配图尺寸约束

- 由 AI 或本地工具生成的概念插图、关系图、流程图和解释图，最终画布必须为 `16:9`；优先输出 `1600×900 px` 或同等比例，不生成 1:1、4:3 或竖版替代图。
- 截图、官方文档裁切图和终端案例属于证据素材，优先保留完整文字与操作上下文，可保留原始比例；如需调整画布，只能加留白，不得为满足 `16:9` 裁掉关键内容。
- 每张正文图在报告中记录实际宽高、比例和素材类型（生成插图/截图/裁切图）；验收时检查生成插图比例误差为 0，截图类检查主体完整、文字可读。

#### 发布脱敏硬规则

- 公众号正文、图片 alt、图注、图片文件名和可发布报告中，严禁出现“用户提供”“用户素材”“用户截图”“投稿截图”“作者截图”等内部来源措辞。统一改写为“案例截图”“界面截图”“终端案例”或可由图片直接核验的事实描述。
- 每张进入发布素材目录的图片都必须逐像素检查可见敏感信息。至少排查：真实姓名、用户名、头像、邮箱、手机号、账号 ID、任务 ID、API key、Token、Cookie、内网域名、IP、机器名、个人路径、项目私有名、二维码和浏览器登录信息。
- 发现敏感内容时，必须在输出图中使用不可逆的纯色遮挡或足够强的模糊/像素化处理；不得只在图注中声明“已脱敏”，不得用 `<name>`、`<user>` 等看似占位符掩盖仍可关联的原值。遮挡区域要覆盖完整字符串及上下文线索，保留原图到备份目录，不覆盖原图。
- 发布前再次用 `view_image` 检查处理图，并逐张记录“已检查敏感项/遮挡位置/验收结果”。任何一张仍能读出个人路径、账号或凭据时，停止交付，不能宣称配图完成。
- 原图来源、处理过程和失败项只写入内部 `gzhwz-processing-report.md`；正文不得暴露来源、处理环境或内部工作流。

对每张图执行：

1. 用 `view_image` 检查原图内容、文字清晰度和是否包含浏览器残片。
2. 按 `imagegzh` 的固定“一号样式”处理：保留原主体、文字、Logo、箭头、数字、布局、颜色和字体；只清理滚动条/浏览器残片/明显多余留白；约 4 px 白色外边距、10 px 圆角、1 px `#d9d9d9` 浅灰边框、极轻阴影；不添加标题、贴纸、图标、水印、装饰图形或新文案。
3. 输出新文件，不覆盖原图；按正文中图片的首次出现顺序，将处理后的文件重命名为 `图一.<原扩展名>`、`图二.<原扩展名>`、`图三.<原扩展名>`……（保留原扩展名和大小写）。同步把 Markdown/HTML 中对应的图片引用更新为新文件名，并写入“原图 -> 处理图（新文件名）”映射。若目标文件名已存在，先核对它是否就是同一张图；无法确认时停止重命名并报告冲突，不覆盖任何文件。
4. 逐张验收：可打开、文字清晰、主体完整、样式一致、圆角和边框紧凑。AI 改动文字或布局时，退回使用本地无损裁切加边框兜底。

#### 正文图片间距与排版

- 一张图片独占一个段落，不在同一段连续堆放多张图片；图片与图片之间必须保留可见的垂直间距。
- 连续配图之间至少间隔一个空段（发布到公众号编辑器后目标视觉间距约 16–24 px）；有明确语义承接时，优先使用简短图注或一两句必要的过渡文字，不能为了拉开距离编造内容。
- 同一组图片需要紧邻展示时，也要逐张分段并保留上述间距；不得让图片边缘、图注或标题直接相贴，影响阅读节奏。
- 交付前在实际发布格式中复核相邻图片的间距；若 Markdown 空行在目标编辑器中被折叠，改用等效的独立空段或段落间距实现，不改变图片内容。

任何一张图未经过上述 `imagegzh` 流程或验收失败，都不得宣称“配图已完成”；保留原图并列出失败项。

#### 3.1 截图参考重绘（可选）

- 当用户明确要求“基于截图生成观感更好的解释图”时，可使用当前环境中已获授权的图片生成工具。先确认工具、计费边界和输出位置，再执行 dry-run；不要在 Skill 文档中写死内部服务地址、账号、密钥或认证方式。无论选择哪条线路，都必须记录实际服务、模型、任务 ID 和验收结果，不得在未授权时创建付费任务。
- 重绘图只承担概念解释、关系示意或决策流程，不替代需要逐字核对的终端案例、官方文档或产品界面截图。提示词应要求保留事实关系，禁止新增可发布文字、账号、路径、令牌、二维码、品牌或水印。
- 重绘或生成的解释图提示词必须明确写入 `16:9` 画布（建议 `1600×900 px`）；生成后若比例不符，先等比裁切或补边到 `16:9`，不得直接拉伸变形。
- 调用前先执行 dry-run；生成后先用 `view_image` 检查文字、布局、比例和敏感信息，再按本节的 `imagegzh` 一号样式输出。原始参考图、任务 ID、提示词、输出尺寸、处理映射和验收结果写入唯一的 `gzhwz-processing-report.md`，实际运行时与失败证据写入 `environment.md`。
- 若生成任务返回认证过期、网络错误或没有可验收文件，不要盲目重试或替换现有成品；记录错误和任务 ID，保留已经验收的原图/成品，待凭据或外部状态恢复后再单独重试。

### 4. 图片编号与正文对应
- 按正文从上到下的首次出现顺序编号：`图一`、`图二`、`图三`……每张只编号一次，装饰图不计入。
- 编号同时作为处理后图片的文件名基名：正文第一张配图对应 `图一.<扩展名>`，第二张对应 `图二.<扩展名>`，依此类推；扩展名沿用原图。不要按原文件名、目录排序或处理完成时间编号。
- 重命名后逐一更新 `.md` 中的图片路径（包括相对路径、HTML `<img src>` 和引用式链接）；除文件名外不改变链接的目录、锚点或其他属性。若同一图片在正文中重复出现，所有引用指向同一个编号文件。
- 逐图检查图片标题/图注：只保留读者理解该图所需的核心事实，优先说明图中对象、动作、结果或关键字段；标题应简短、清晰、可由图片或原稿核验，优先压缩为一句话。
- 图注只描述图片事实和阅读价值，不描述图片来自谁、由谁提供或如何采集；发布正文中不得出现任何内部素材来源说明。
- 删除与图片无直接关系的背景介绍、过程复述、价值宣传、情绪化形容、重复正文和“本文将……/下面介绍……”式导语；不要把图注写成段落或小作文，避免“读者可以据此复查”“而不是只能相信……”等解释性长句。
- 一个图片只保留一个标题/图注；已有标题不满足上述标准时直接精简或改写，不叠加多个版本。无法从图片或原稿确认的内容不写入标题，列入待确认项。
- 复核正文引用顺序、文件名/路径、图注编号、备份映射和图片总数一一对应；最终应能从 `.md` 中的 `图一`、`图二`……引用反查到同名图片文件。
- 正文配图集中存放：发布前必须在文章专属素材目录下建立唯一的 `正文配图/` 文件夹，仅放入正文实际引用的 `图一`、`图二`……文件；原始截图、处理中间文件、二维码和封面不得混入该文件夹。Markdown 中所有正文图片引用必须统一指向 `正文配图/图一...`，并按首次出现顺序连续命名。

### 5. 链接与埋点：按阅读阶段自然承接

正文处理完成后，先建立埋点清单，再判断读者在各阶段可能需要的下一步并插入正文。埋点应是内容服务的自然延伸，而不是脱离语境的广告：每个入口都必须回答“读者为什么此刻需要它”。每篇文章默认至少插入 1 个可核验埋点；正文超过 800 字或包含 3 个以上二级标题的中长文，至少插入 2 个，其中至少 1 个位于 `opening`、`contextual` 或 `decision` 阶段。文末微信 CTA 是默认必有的 `closing` 埋点，不得因“没有自然入口”省略。用户明确要求不放 CTA 时才允许记录豁免原因，但仍须将埋点闸门标为 `blocked`，不能把该文称为完全可发布。不得为了凑数量改写正文或堆叠 CTA。

需要起草入口文案或填写报告时，读取 [references/tracking-examples.md](references/tracking-examples.md)。历史文章标题只能从 [references/historical-article-catalog.md](references/historical-article-catalog.md) 中选择；用户确认某篇新文章已经发布，并提供标题或后台截图后，可以把它追加到目录再使用。模板只用于结构参考，所有占位符必须替换为已核验的真实信息，不能原样发布。

#### 5.1 埋点位置矩阵

按语义节点判断位置，百分比只用于辅助检查，不要求机械计算字数：

| stage | 参考位置 | 数量与作用 |
| --- | --- | --- |
| `opening` | 开头约 0%–15% | 最多 1 个。降低阅读决策成本，可承接目录、核心结论、本文阅读承诺或高度相关的前置文章；不得在尚未提供价值时强行销售。 |
| `contextual` | 正文约 20%–75% | 在刚解决一个问题、产生下一个问题或需要证据的位置插入。建议每 500–800 字最多 1 个，单篇通常不超过 3 个。 |
| `decision` | 正文约 75%–90% | 最多 1 个主要入口，用案例、清单、完整教程、工具或权威证据帮助读者决定下一步。 |
| `closing` | 总结之后 | 先相关资源（如有），再网站 CTA，最后微信 CTA；网站和微信必须是两个独立区块。 |

- 位置服从语义：短文可以没有 `opening`、`contextual` 或 `decision`，但不能因此变成零埋点；长文也不能因篇幅机械增加无关链接。
- 同一目标原则上只出现一次；确需重复时，必须面向不同阅读意图，并在报告中说明原因。
- 网站不只允许出现在文末：当正文刚完成一个可执行步骤、需要工具或需要继续实践时，可以把已核验的站内页自然嵌入该段文字。正文网站入口仍遵守密度和上下文规则，文末只保留一个主网站 CTA。
- 禁止连续段落重复 CTA、与上下文无关的链接、用多个入口争夺同一个动作，以及用“点击这里”等无法预判目标的孤立锚文本。
- 文首、文中或决策阶段没有自然入口时，在报告中写“无自然入口 + 原因”，不视为失败；这只适用于对应阶段，不得用来跳过 `closing-wechat-01`。`closing` 的网站和微信规则仍按本节执行。

#### 5.2 入口意图与软性文案

每个入口只选择一个主要 `intent`：

- `continue-reading`：目录、继续阅读或相关阅读，帮助读者补齐前置知识或深入当前主题。
- `get-resource`：清单、模板、完整教程或资料，承接可执行需求。
- `verify-evidence`：案例、数据来源或权威资料，补足证据和信任。
- `take-action`：工具、报名、试用或网站操作，让读者完成明确任务。
- `ask-or-connect`：评论区提问、关键词互动或微信交流，承接个性化问题。

入口文案先连接刚读完的内容，再说明下一步能解决什么，最后给出明确目标。例如：“如果你正在处理同样的问题，可以先看这份清单。”避免“重磅”“速领”“错过后悔”等夸张措辞，不虚构福利、名额、截止时间、客服身份、回复时效或资料领取机制。入口宜使用一两句正文式表达，不默认制作醒目广告卡片、按钮墙或重复分隔模块。

#### 5.3 历史文章：标题式链接模式

微信公众号后台可以直接从“已发表内容”中选择文章绑定到正文文字。默认采用“先写标题、后由作者绑定”的模式，交付正文不放历史文章 URL、Markdown 链接或 UTM：

- 只从 `references/historical-article-catalog.md` 选择与当前段落高度相关的文章；当前目录是用户截图提供的临时白名单，不得凭空补充其他文章。
- 正文中把可点击文字直接写成已发表文章的准确标题，统一使用 `《文章标题》`；不要写“点击这里”、内部编号、日期或“相关文章 1”。
- 用户在公众号编辑器中选中 `《文章标题》`，点击超链接，选择“已发表内容”，再搜索并绑定同名文章。技能交付的是可见文案和绑定目标，不代替用户在后台选择文章。
- 标题必须与目录和公众号后台显示一致；标题不确定、截图模糊、搜索不到或文章已删除时，不写入正文，列入“待确认/未采用清单”。
- 同一篇历史文章原则上只绑定一次；确需重复时，必须说明两处分别服务于不同阅读意图。
- 按正文语义筛选高度相关的文章，优先放入最匹配的 `opening`、`contextual` 或 `decision` 节点；只有多篇资源共同服务于总结后的深读需求时，才在正文结束前增加独立“相关阅读”区块。
- 不再要求历史文章 URL 核验或 UTM；后台绑定完成后，报告将 `url` 记为“由公众号后台绑定”，`utm_status` 记为“不适用”。
- 用户确认新文章已经发布后，可根据标题或后台截图追加到标题目录；追加时记录发布日期和来源，未确认已发布的标题不得进入目录或正文。

如用户明确提供了某篇文章的真实 URL，仍可在报告中记录作核对依据，但正文继续优先使用标题式绑定，除非用户另行要求输出 URL。

#### 5.4 事件记录与 UTM

在唯一的 `gzhwz-processing-report.md` 中为每个入口记录一行，字段不得省略：

| 字段 | 规则 |
| --- | --- |
| `event_id` | 全文唯一、稳定、可读，格式为 `<stage>-<purpose>-<NN>`，例如 `opening-summary-01`、`contextual-case-02`；修改文案不随意改 ID。 |
| `stage` | `opening`、`contextual`、`decision` 或 `closing`。 |
| `position` | 精确到标题、段落、图片或总结之后，不只写“文中”。 |
| `intent` | 使用 5.2 中的一个主要意图。 |
| `target_type` | 历史文章、站内页、外部资料、互动入口、网站 CTA 或微信 CTA。 |
| `target_title` / `url` | 历史文章写目录中的准确标题，`url` 固定写“由公众号后台绑定”；网站或外部资料写真实 URL；无 URL 的互动或二维码入口标记“不适用”。 |
| `utm_status` | 历史文章写“不适用：由公众号后台绑定”；网站按本节规则添加；其他入口写不可添加、不适用或待确认，并说明原因。 |
| `verification_status` | 写已核验、未采用或待确认；待确认项不得出现在可发布正文中。 |
| `copy_role` | 承诺、补充、证据、行动或关系承接。 |
| `post_publish_metrics` | 阅读、点击、深读、关注、评论、咨询、转化；没有发布后数据时逐项写“待记录”，不得填 0 或估算值。 |

- 每篇报告在事件表后必须增加埋点闸门摘要：`inserted_event_count`、`required_minimum`、`gate_status`（`passed`/`blocked`）和 `exception_reason`。正文中没有任何已插入事件，或中长文少于最低数量时，`gate_status` 必须为 `blocked`，不得进入封面标题确认闸门。
- `closing-wechat-01` 的正文文案、二维码引用和报告记录必须一一对应；没有可核验网站 canonical URL 时，将 `closing-website-01` 记录为“待确认/未插入”，不得填猜测 URL，但不能影响微信埋点的插入。
- 最低埋点配置：每篇必须有 `closing-wechat-01`；存在可核验 canonical URL 时，必须另有 `closing-website-01` 并按规则添加 UTM。中长文还必须从 `opening`、`contextual`、`decision` 中选择至少一个与正文语义匹配的入口。

- `article_id` 由文章目录或标题生成，全文保持稳定、可读；不包含 token、Cookie、用户标识或其他敏感信息。
- 可控制参数的网站链接，无论出现在文首、正文还是文末，都使用 `utm_source=wechat&utm_medium=article&utm_campaign=<article_id>&utm_content=<event_id>`；已有查询参数时按 URL 结构正确追加，不改变核心路径或覆盖业务参数。
- 历史微信文章采用标题式绑定，不输出 URL，`utm_status` 记录“不适用：由公众号后台绑定”；外部权威资料或其他不能安全追加参数的链接保留原 URL，并记录“不可添加 + 原因”。
- 网站没有可核验 canonical URL 时写“待确认”，不得猜域名，也不得把占位 URL 插入可发布正文。
- 正文入口文字、`event_id`、报告记录和后台绑定目标必须一一对应；二维码等无 URL 入口仍需记录事件，但 `url` 与 `utm_status` 标记“不适用”。

#### 5.5 文末承接顺序

总结之后的引流区块固定按以下顺序放置：相关资源（如有）→网站 CTA→微信 CTA。不要把两种入口揉成一句话：

1. **网站引流在前。** 依据文章主题只选择一个主 CTA，承接读者刚完成的阅读任务，说明去目标网站能继续做什么。链接优先使用原文、项目配置或用户明确提供的 canonical URL；没有可核验 URL 时记为“待确认”，不在正文猜写域名。
2. **微信引流在后。** 网站 CTA 之后另起一段，使用用户明确提供并确认可发布的二维码或联系方式，邀请读者就文章主题、实际问题或合作需求继续交流。不要虚构微信号、姓名、公众号名称、客服身份或承诺回复时效。

微信入口不是本仓库的默认资产。执行文章任务时：

- 没有用户明确提供并确认的二维码或联系方式时，记录为“待补充”，不要猜测或调用本机默认资产。
- 将二维码复制到文章的图片目录或发布素材目录后再引用，正文不得引用本机绝对路径或临时目录。
- 二维码属于结尾 CTA 素材，不计入正文配图数量，不命名为 `图一`、`图二`，也不参与正文配图编号。
- 不调用 `imagegzh` 改造二维码，不裁切、不加圆角/边框/阴影、不重新生成或有损压缩，保持用户提供的源文件像素不变，避免影响扫码。
- 用户明确提供其他微信二维码时，以用户本轮提供的图片为准；只替换微信区块图片，不改变“网站在前、微信在后”的顺序。

微信区块必须单独复核并在交付报告中明确给出结果：二维码文件存在且可打开、正文引用无断链、文案明确邀请微信交流、区块位于网站 CTA 之后且为文章最后一个引流区块。不能把网站 CTA 当作微信引流。

### 5.6 封面标题确认与生成闸门

这是正文、配图、链接埋点和二维码处理完成后的强制停顿点。没有用户明确选择标题时，不得生成封面，也不得提前调用任何封面生成或设计技能。

1. 先完成本技能前 5 个阶段，并通过图片、正文、链接、埋点硬闸门和脱敏检查。
2. 停止当前工作，只向用户提供 3–5 个公众号标题候选。候选标题必须来自正文事实，说明核心对象、问题、动作或结果；不得出现“未核验”“待确认”“用户提供”“AI 生成”“处理记录”等内部状态词。每个候选标题附一句适合的读者入口说明，不生成封面预览。
3. 等用户明确选择一个标题，或明确要求重新拟题。用户只说“继续”“生成封面”而没有选定标题时，继续停留在本闸门并要求选择标题。
4. 标题确定后，把选定标题写入封面生成记录，并以它作为唯一封面主标题。封面生成过程按以下技能分工执行，不能把分工混成一个未记录的提示词：
   - `baoyu-cover-image`：确定封面类型、配色、渲染方式、文字层级、情绪和可用比例。
   - `banner-design`：核对单张公众号横版封面的安全区、标题可读性、视觉焦点和平台尺寸；目标输出比例固定为 `2.35:1`，推荐尺寸 `940×400 px`，不生成 1:1 配套图或其他尺寸版本。
   - `design`：复核品牌色、字体层级、留白、信息密度和标题与画面的关系。
   - 图片生成后端：按用户指定或当前可用配置执行。实际后端不得擅自切换，外部计费任务必须以用户明确授权为前提；认证信息只从当前环境的安全配置读取，不写入文章、报告或仓库。
   - `imagegen`：仅在需要独立探索风格或生成备选概念时使用；若用于最终封面，必须记录实际调用方式，并且不能在后端已由用户确定后擅自替换该线路，避免同一封面重复生成而未说明。
5. 封面提示词必须包含已选标题、文章主题、目标读者、画面主体、构图方向、配色、`2.35:1` 比例、`940×400 px` 画布和文字安全区；禁止添加未经核验的品牌、数字、人物、Logo、二维码、账号、路径、真实域名或新事实。封面中的标题文字优先由当前环境中可复核的排版工具叠加，以避免模型生成错字。
6. 只生成一张公众号横版封面，最终输出尺寸固定为 `940×400 px`，宽高比必须为 `2.35:1`（比例误差为 0）。封面放在文章专属发布素材目录，不得放入 `正文配图/`，不参与 `图一`、`图二` 编号；不要生成或保留 1:1 配套图及其他尺寸版本。报告记录标题、技能分工、任务 ID、实际尺寸、比例偏差和验收结果。
7. 生成后必须用 `view_image` 检查标题缩略图可读性、主体完整性、平台安全区和敏感信息。封面生成成功不等于文章可发布；比例偏差、文字错漏或版权风险必须列入待确认项。

### 6. 交付前复核
- 通读正文，检查事实、数字、引用、标题层级、错别字、标点、链接、CTA 和微信引流文案。
- 逐个检查入口是否与前后内容自然衔接、能说明此刻出现的理由，并确认没有连续段落 CTA、生硬广告块或为了凑数插入的不相关文章。
- 检查 `opening`、`contextual`、`decision`、`closing` 的实际分布和数量：文首最多 1 个，正文入口符合语义和密度要求；缺失阶段必须在报告中记录“无自然入口 + 原因”。
- 复核重复目标：同一目标原则上只出现一次；确需重复时，报告中必须说明不同阅读意图。确认文末只有一个主网站 CTA。
- 逐条复核链接清单：已插入、未采用和待确认入口的 `event_id`、阶段、意图、目标类型、精确位置、文案角色和核验状态完整；历史文章入口必须是目录内准确标题，待确认项没有进入可发布正文。
- 检查每个 `event_id` 全文唯一；网站入口与 `utm_content` 一一对应，历史文章入口与正文标题和后台绑定目标一一对应，二维码等无 URL 事件已正确标记“不适用”。
- 执行埋点硬闸门：正文至少有 1 个已插入事件；中长文至少有 2 个且至少 1 个位于 `opening`、`contextual` 或 `decision`。报告中的 `inserted_event_count`、`required_minimum` 和 `gate_status` 必须一致；不满足时先补埋点或记录用户明确豁免，不得继续交付或生成封面。
- 核对 UTM 参数是否稳定、可读且未改变目标 URL 的核心路径或业务参数；没有 canonical URL 时确认正文未出现猜测域名。
- 检查发布后指标字段包含阅读、点击、深读、关注、评论、咨询和转化；尚无数据时统一写“待记录”，不得用 0、估算或虚构数值代替。
- 再逐张检查图片可打开、文字清晰、样式统一、编号连续、原图仍在备份目录、正文引用无断链；同步检查每个图片标题/图注是否只保留必要事实、没有啰嗦或无关介绍，且与对应图片一致；另行检查默认微信二维码保持原样且位于网站 CTA 之后。
- 复核正文标题和图注，清除“未核验”“没核验”“待确认”等内部状态词及其他与主题无关的 AI 生成痕迹；复核相邻正文图片均有独立段落和可见间距，不因排版过密连续相贴。
- 最后执行正文配图目录闸门：统计 Markdown 中正文图片引用，与 `正文配图/` 中的文件逐项比对；确认目录只包含按首次出现顺序命名的 `图一`、`图二`……，没有缺号、重号、未引用图片、原始截图、封面或二维码。发现不一致时，先整理目录并修正引用，再进入发布交付。
- 做一次发布脱敏闸门：全文搜索并清零“用户提供”“用户素材”“用户截图”“投稿截图”等措辞；逐张放大检查发布图中的姓名、路径、账号、令牌、内部域名、任务标识和登录信息。任一命中都必须回到图片处理步骤重新遮挡，不能仅修改文字说明。
- 确认本篇只有一个 `gzhwz-processing-report.md`，且其中同时包含图片处理、备份映射、链接埋点和最终验收；发现重复报告时合并信息，不新增同类文件。
- 如果用户尚未选择公众号标题，必须停在“封面标题确认与生成闸门”，不得报告封面完成，也不得调用封面生成技能。
- 如果用户已经选择标题，确认报告记录了标题、封面技能分工、输出路径、尺寸、比例和敏感信息验收。
- 只有正文、图片、网站 CTA、微信引流和待补项都已核对，才报告完成；存在待确认链接或微信入口时必须明确列出，不能称为“完全可发布”。

#### 6.1 正文与对话隔离硬闸门

- 发布正文只能面向读者叙述主题、事实、操作和判断，不得出现与用户、作者和编辑过程的对话痕迹。禁止写入“用户提供/用户截图/作者截图/根据你的要求/本轮处理/本次任务/我们已经/我帮你/请补充”等措辞，也不得出现对话回顾、工具调用结果、失败重试说明或交付状态。
- 禁止把内部工作区和处理记录带入正文，包括本机绝对路径、`manual/`、`source/`、`online/`、`manifest.tsv`、`environment.md`、`gzhwz-processing-report.md`、`TODO.md`、任务 ID、凭据错误、素材备用区和“待补图/待确认”清单。需要保留的操作步骤必须改写成读者可执行的相对路径或通用示例。
- 逐段检查“本文/本篇”是否只是自然的内容指代；凡是指向编辑、截图、素材、发布或处理流程的句子，一律删除或改成读者可以直接执行的说明。技术语境中的合法术语（例如 Git commit 的 author、作者身份字段）不作误判，但不得借此谈论文章作者或用户。
- 交付前对正文、图片 alt、图注和可发布链接文案做关键词扫描，并人工复核命中上下文。扫描命中内部词时必须回到正文修改，不能只在报告里解释“这是编辑备注”。唯一处理报告保留审计证据、失败记录和待确认项，绝不复制回正文。

## 交付格式

- 按用户指定格式交付完整正文，保留 Markdown/HTML/Word 结构和链接。
- 交付报告和最终回复只给一行“处理环境”摘要，并附完整内部记录的路径；不要在开头展开 OS、Shell、未使用运行时、包管理器或技能版本清单。
- 交付处理后的新图片、备份目录和“原图 -> 输出图”映射，回复中列出绝对路径。
- 简要说明验证结果，并单独列出已插入链接、未采用/待确认链接、UTM 状态，以及仍需用户补充的真实链接、微信号、公众号或二维码。公众号后台发布动作不由本 Skill 代替执行。
- 若处于标题确认闸门，交付只包含标题候选和等待用户选择的说明，不生成封面。
- 标题选定并完成封面后，额外交付封面绝对路径、生成任务 ID、实际尺寸、比例偏差、使用的技能分工和封面待确认项。

## 失败与边界

- 输入不是可编辑文章或图片时，说明可处理范围并请求可读文件，不假装完成。
- 浏览器不可用、登录态失效或公众号页面无法访问时，按可选降级处理：不阻断其他文章流程，但必须报告未完成的链接核验项；不得索取或记录登录凭据。
- 任何覆盖原图、破坏图片文字、改动事实或引入未核验联系方式的操作均视为失败，应回退到备份并报告具体问题。
