# 公众号文章阶段化埋点模板

仅在设计入口文案或填写 `gzhwz-processing-report.md` 时读取本文件。历史文章标题必须来自 `historical-article-catalog.md`。`<...>` 均为占位符，必须替换为已核验信息；无法核验时记入待确认清单，不得原样发布。

## 最低埋点闸门

- 每篇文章至少插入 1 个可核验事件，默认使用文末 `closing-wechat-01`；除非用户明确要求不放 CTA，否则不能省略。用户豁免时须记录原因，并将埋点闸门标为 `blocked`。
- 正文超过 800 字或包含 3 个以上二级标题时，至少插入 2 个事件，其中至少 1 个位于 `opening`、`contextual` 或 `decision`。
- 有可核验网站 canonical URL 时，必须加入 `closing-website-01` 并添加 UTM；没有 canonical URL 时只在报告记录待确认，不得把占位 URL 放进正文。
- 报告必须写 `inserted_event_count`、`required_minimum`、`gate_status` 和 `exception_reason`；数量不达标时先补埋点，不能进入封面生成流程。

## 标题式历史文章埋点

历史文章默认不输出 URL。正文直接写目录中的准确标题，用户在微信公众号编辑器中选中标题后，从“已发表内容”搜索并绑定：

```markdown
如果你还在熟悉 Codex 的工作方式，可以先看《别再把 Codex 当成“会写代码的 ChatGPT”：一文看懂它到底怎么工作》，再回到本文继续配置自动化。
```

绑定说明只给编辑者看，不粘贴进正文：选中 `《别再把 Codex 当成“会写代码的 ChatGPT”：一文看懂它到底怎么工作》` → 编辑超链接 → 已发表内容 → 搜索同名文章。

报告记录示例：

```text
target_type: 历史文章
target_title: 别再把 Codex 当成“会写代码的 ChatGPT”：一文看懂它到底怎么工作
url: 由公众号后台绑定
utm_status: 不适用：由公众号后台绑定
verification_status: 已核对标题，待作者在后台绑定
```

## 正文网站埋点

网站不必等到文章结尾才出现。刚完成一个步骤、需要工具或准备继续实践时，可以把站内页嵌入正文句子；只使用已核验的 canonical URL，并为每个位置使用独立的 `utm_content`：

```markdown
如果你准备把刚才的检查流程迁移到自己的项目，可以继续看《从任务描述到验证提交的完整闭环》，里面补充了目标、范围和验收条件的写法。
```

这里的《从任务描述到验证提交的完整闭环》绑定的是已发表文章；如果目标是网站页面，则写成：

```markdown
如果你想继续实践这套方法，可以到 CodexGuide 的 `<栏目或教程名称>` 查看完整步骤。
```

网站链接示例：`https://codexguide.io/<path>?utm_source=wechat&utm_medium=article&utm_campaign=<article_id>&utm_content=contextual-site-01`。
文末仍保留一个主网站 CTA，不要因为正文已有网站入口而重复堆叠多个结尾链接。

## 文案模板

### 文首：阅读承诺或前置内容

适用于读者需要先判断文章是否值得继续读，或确实存在必要的前置知识。最多选一个方向。

```markdown
这篇文章会把 `<核心问题>` 拆成 `<范围或步骤>`。如果你只想先解决 `<最迫切的问题>`，可以直接看 `<章节名或已核验资源标题>`。
```

```markdown
如果你还不熟悉 `<前置概念>`，可以先读 `<已核验历史文章标题>`；已经了解的读者，直接往下看操作部分即可。
```

不要在文首同时放目录、历史文章、网站和微信入口，也不要在尚未提供价值时要求关注、咨询或领取资料。

### 文中：问题解决后的下一步

紧跟在相关结论、步骤、案例或图片之后，先连接上下文，再说明目标内容的用途。

```markdown
做到这里，`<当前问题>` 已经解决。接下来如果你需要 `<下一步任务>`，可以继续看 `<已核验资源标题>`，里面补充了 `<具体价值>`。
```

```markdown
上面的判断需要结合真实场景验证。`<已核验案例标题>` 记录了 `<可验证内容>`，适合用来对照自己的情况。
```

```markdown
如果你正在处理同样的问题，可以先用这份 `<清单/模板/教程名称>` 逐项检查，避免遗漏 `<具体风险>`。
```

### 文末：网站继续实践与微信交流

先总结文章，再依次放置两个独立区块。

```markdown
如果你准备继续完成 `<明确任务>`，可以到 `<网站或栏目名称>` 查看 `<已核验内容或工具>`：[`<明确链接文案>`](<带合规 UTM 的 canonical URL>)。

如果你的情况涉及 `<文章无法覆盖的个性化变量>`，可以扫码添加微信，带着 `<建议准备的信息>` 一起交流。

![微信二维码](<发布素材目录中的二维码相对路径>)
```

网站文案说明下一步动作，不写泛化的“了解更多”。微信文案只承接个性化交流，不承诺回复时效、诊断结果或未提供的服务。


## 发布前快速检查

- 每个入口能解释“为什么此刻出现”，去掉后不会暴露生硬的广告断点。
- 每篇至少 1 个已插入事件；中长文至少 2 个且至少 1 个位于 `opening`、`contextual` 或 `decision`。
- 文首最多 1 个入口；正文没有连续段落 CTA；同一目标没有无理由重复。
- 锚文本能预判目标内容，不使用孤立的“点击这里”“立即查看”。
- 每个 `event_id` 全文唯一，正文、报告和 `utm_content` 一致。
- 未核验链接、占位符和待确认 canonical URL 没有进入可发布正文。
- 结尾保持相关资源（如有）→网站 CTA→微信 CTA，二维码是最后一个引流区块。
