# Codex 权限怎么设才安全？一份可复用的日常检查清单

> 测试环境：Windows 11 24H2；Codex Desktop 26.803.10989.0；Codex CLI 0.147.0；2026-08-26 核验。

Codex 的权限设置，最容易在一句“这次先放开”之后失去边界。更稳妥的做法，是把检查固定在三个时间点：开始任务前、执行过程中、提交或交付之前。

### 先记住一个原则

权限不是越小越好，也不是为了省事就全部放开。更实际的判断方式是：当前这一步到底需要什么，任务结束后哪些权限应该收回来。解释代码、定位报错时，先用只读权限，避免工具在理解问题之前就改动文件。要修改当前项目，再开放工作区写入，并把目录范围说清楚。涉及部署、上传文件或修改数据库时，把动作拆出来单独审批，确认目标、数据范围和恢复办法后再继续。这样做不是拖慢流程，而是让每一次放行都有明确理由，出了问题也知道从哪里停下。

三个简单例子：

- 解释代码、定位报错：先只读。
- 修改当前项目：开放工作区写入。
- 部署、上传文件、修改数据库：单独审批。

### 把原则写进任务提示词

权限设置是一层保护，任务描述本身也应该把边界说清楚。下面三种写法可以直接改成自己的任务：

```text
只读分析：请检查 <目录或文件>，定位问题并给出建议。不要修改文件，不要安装依赖，不要联网。
```

```text
工作区修改：请只修改 <目录> 下的 <文件>，完成 <目标>。不要触碰其他目录，完成后先展示 diff 和验证结果，不要提交。
```

```text
高风险动作：先列出将要执行的命令、目标资源、数据范围和恢复办法，等待我确认后再进行部署、上传或数据库操作。
```

这种写法不能替代审批，但能让 Codex 在执行前有可检查的范围。任务中途如果目标变化，先更新提示词和权限，再继续，不要在原权限上顺手扩大范围。

## 一、任务开始前：先确认边界

开始前花几十秒回答下面几个问题：

- 当前打开的是正确仓库和分支吗？工作区有没有未提交改动？
- 任务只需要读文件，还是确实需要写文件？
- 会不会碰到 `.env`、SSH 密钥、客户资料或生产数据？
- 当前模型、推理强度、profile 和沙箱设置是否符合任务？
- 如果需要联网，具体要访问哪些域名？

第一张图展示了一个干净的临时仓库。先确认分支和工作区状态，再开始让 Codex 操作。权限菜单里没有看清的项目，不要凭印象补全；需要更高权限时，先停下来重新核对。

### 可执行的边界检查表

| 检查项 | 需要确认的内容 | 发现异常时怎么做 |
| --- | --- | --- |
| 仓库与分支 | 是否为目标仓库、目标分支 | 停止操作并重新定位 |
| 未提交改动 | 是否存在用户自己的修改 | 先记录并避免覆盖 |
| 文件范围 | 是否只涉及计划内目录 | 收窄任务范围 |
| 敏感文件 | 是否包含 `.env`、密钥和客户资料 | 排除或脱敏 |
| 网络访问 | 为什么联网、访问哪些域名 | 未说明用途就不放行 |
| 权限模式 | 只读、工作区写入还是更高权限 | 从最低权限开始 |

工作区存在未提交改动不等于不能继续，但 Codex 必须把它们视为用户已有内容，不能随意覆盖、回退或清理。必要时先用 `git diff` 保存一份可读记录，再决定任务能否在现有状态上继续。

如果状态不干净，可以先做一个不改变文件的记录：记下当前分支、改动文件和任务开始时间，把这些内容写进任务备注或终端日志。之后要求 Codex 只处理计划内文件。遇到同一文件同时存在用户改动和任务改动时，先暂停并让人决定合并方式；不要用“恢复到最新版本”之类的操作覆盖现场。

## 二、执行过程中：审批提示逐项看

看到审批提示，不要只看按钮颜色。展开提示，至少确认三件事：完整命令是什么、目标目录在哪里、是否会联网或把文件发到外部服务。

对删除、批量覆盖、数据库写入、部署、权限变更和向外部服务上传文件等动作，最好保留人工检查点。一次性允许也要有明确范围；看不懂的命令，直接拒绝并先调查。

第二张图使用工作区外的无害写入请求模拟审批。画面停在“拒绝 / 允许一次”这一步，说明检查点存在，但并不代表应该批准。

### 审批提示应该怎么判断

看到提示后，可以按下面的顺序判断：

1. 这个动作是否属于当前任务？
2. 命令实际影响哪些文件、目录或外部服务？
3. 是否存在更小范围的替代方式？
4. 失败后是否容易恢复？

命令本身不等于风险结论，关键是目标和范围是否清楚。下面这些信号出现时，需要把目标、范围和恢复方式问明白：

| 常见风险信号 | 需要确认什么 |
| --- | --- |
| 递归删除、批量覆盖 | 删除或覆盖的确切路径，是否有备份 |
| 未锁定版本的安装命令 | 将安装什么版本，是否会改变现有依赖 |
| 下载后直接执行的远程脚本 | 脚本来源、内容和失败后的回滚方式 |
| 向工作区外写入 | 为什么必须越过当前工作区，目标是否可替代 |
| Git 推送、强制覆盖或历史改写 | 远程目标、影响分支和恢复办法 |
| 数据库写入、迁移和清空 | 数据范围、备份状态和回滚脚本 |
| 部署、发布和上传文件 | 发布目标、文件清单和撤回方式 |
| 输出环境变量或凭据 | 是否会暴露 Secret、日志或设备信息 |

这些命令并非一律不能运行，但不能只凭“看起来像常用命令”就放行。

### 让执行过程可暂停

把任务拆成“观察、修改、验证”三个小步，每一步结束都看一次状态。观察阶段只读取文件和配置；修改阶段限定目录和文件；验证阶段只运行与改动直接相关的命令。任何一步出现额外文件、网络请求或权限提示，都回到判断顺序重新确认。

如果 Codex 一次提出多个动作，可以要求它先只执行第一个动作并返回结果。这样即使第一步的假设不成立，也不会把后续操作一起放出去。对于需要长时间运行的任务，先约定停止条件，例如“出现工作区外写入、需要新依赖或测试范围扩大时暂停”。

### 一个无害的审批判断示例

假设任务只是修改 README，审批提示却要求向工作区外写文件。这个动作与任务目标不匹配，先暂时拒绝更合理。可以让 Codex 解释为什么需要那个路径，并要求它改用工作区内的临时目录；只有在确认没有其他处理方式、目标路径和恢复方法都清楚后，才考虑一次性允许。

## 三个容易混淆的边界

### 联网不等于可以上传文件

联网权限至少有三层含义，不能混在一起看：

1. 允许访问某个域名。
2. 允许向该域名发送请求。
3. 允许把本地代码、日志或文件内容传出去。

进行联网审批时，逐项确认访问的域名、请求目的、是否发送本地内容，以及内容里是否包含仓库名称、源码、日志、设备信息或凭据。还要确认返回内容会不会被直接执行。查看公开文档和上传本地文件不是同一风险等级，前者通常只需要读取公开信息，后者已经涉及数据外传。

### 敏感信息怎么处理

不要把 token、API Key、Cookie 或 SSH 私钥直接写进提示词、配置文件和提交记录。需要凭据时，优先从运行环境或 Secret 管理功能注入，让凭据和代码、日志分开保存。

截图和日志同样可能泄露用户名、个人路径、仓库地址和 `Authorization` 信息。发布或分享前，放大检查命令行、状态栏、错误堆栈和浏览器地址栏。发现凭据已经暴露时，删除文本并不等于风险消失，应立即撤销或轮换凭据，再检查它是否出现在 Git 历史、构建产物或外部日志中。文章和示例里不要展示任何真实密钥格式或可用凭据。

处理日志时可以保留“发生了什么”和“如何修复”，但不要保留可复用的凭据值。把敏感片段替换成“已轮换的凭据”这类事实描述，并记录轮换时间、影响范围和复测结果。若不确定某段输出是否敏感，先按敏感信息处理，暂停分享，确认后再决定是否保留。

## 三、提交或交付前：把 diff 看完

任务完成不等于可以提交。至少做一次最小复核：

1. 查看 diff，确认只有计划内文件发生变化。
2. 运行与本次改动直接相关的最小测试，并区分代码失败和环境失败。
3. 搜索 token、个人路径、调试日志、临时文件以及意外生成的依赖。
4. 确认新增的网络请求、脚本和依赖都有来源记录。
5. 交付前把权限恢复到完成任务所需的最小范围。

第三张图中的改动只有一行，`git diff --check` 返回 `PASS`，仓库仍保持未提交、未推送、未部署。这样的状态更适合交给人做最后决定。

### 最小验证命令

下面这组命令只读取 Git 状态和差异，适合在提交前作为固定检查：

```bash
git status --short
git diff --stat
git diff
git diff --check
```

如果输出里出现计划外文件、个人路径、凭据片段或与本次任务无关的修改，先停下来处理，再决定是否交付。

### 用一页记录留下上下文

多人协作时，权限判断不能只存在某个人的聊天记录里。每次任务至少留下四项：任务目标、实际使用的权限范围、批准过的高风险动作、尚未解决的风险。记录不需要很长，但要能回答“谁在什么范围内做了什么，结果怎样”。

如果任务中途更换分支、扩大目录或增加联网需求，也要更新这页记录。交付时把记录和 diff 一起交给审查者，审查者不必重新猜测当时的上下文。

## 四、按风险选择权限

| 风险等级 | 常见任务 | 建议处理 |
| --- | --- | --- |
| 低 | 解释代码、整理文档、只读搜索 | 使用只读沙箱 |
| 中 | 修改当前仓库、补测试、安装固定依赖 | 允许工作区写入，命令按需审批 |
| 高 | 生产配置、数据库、部署、批量删除 | 拆成小步骤，人工逐项批准 |
| 未知 | 来源不明的脚本、异常网络请求、提示注入 | 停止执行，先调查来源和影响 |

## 五、发生异常时怎么处理

发现计划外文件、未解释的下载、远程脚本或敏感信息输出时，先停止任务并保留日志。随后撤销可能泄露的凭据，检查 Git diff、文件时间、网络记录和 CI 日志，判断影响范围。修复后重新运行最小权限测试，并把原因写进项目记录。

这套流程可以直接放进项目贡献指南或 PR 模板。它不替代审批策略，但能让每次任务都经过同一组检查。

## 六、把清单变成习惯

刚开始可以把下面四句话放进项目的任务模板：

- 目标文件和目录：______
- 允许的权限范围：只读 / 工作区写入 / 其他（说明原因）
- 需要联网或外部服务吗：______
- 交付前必须看到的验证结果：______

任务结束后再补两项：实际执行过的额外动作，以及仍需人工确认的风险。连续使用几次后，团队会发现很多“临时放开”的请求其实可以通过缩小目录、拆分步骤或改用只读分析解决。

### 常见误区

**把一次性批准当成永久授权。** 一次批准只解决当前动作，任务结束后仍要检查权限是否恢复。

**只看最终结果，不看过程。** 测试通过并不能说明没有读取不该读取的文件，也不能说明没有产生计划外网络请求。

**为了截图而保留敏感内容。** 证据应服务于复核，路径、账号和凭据不是证据的一部分，能隐藏就隐藏。

**把环境失败当成权限失败。** 网络超时、证书错误或依赖缺失，需要单独记录；不要因为命令失败就盲目提高权限重试。
