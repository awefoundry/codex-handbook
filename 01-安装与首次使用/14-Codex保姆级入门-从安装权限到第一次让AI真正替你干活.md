# Codex 保姆级入门：从安装、权限到第一次让 AI 真正替你干活

最近这两个月，用 Codex 的时间非常长，远超我自己 ClaudeMax 20X，不是偶尔打开问一句“这个代码怎么改”，而是每天真的把它当成一个能干活的
AI 工程师来用。

因为代码的问题和 CLI 命令行的事情，很多人都望而却步，但最近几次 Codex
的更新让编程这个事情变得简单起来，甚至好玩起来，是一个人人都可以玩的工具了，让我觉得有必要写一篇长文来让更多人用起来。

以前很多人理解 AI 编程，大概停留在两个画面：

第一，把代码复制到 ChatGPT 里，让它解释一下。

第二，在 IDE 里开一个代码补全工具，让它补几行函数。

但Codex 它不是“帮你写一段代码”，而是“帮你推进一个任务”，是真正的 人人可以用的 agent。

![Codex 实操界面与结果](../图片素材/01-安装与首次使用/Codex保姆级入门-从安装权限到第一次让AI真正替你干活/01-Codex实操图-01.jpg)

我会把官方视频里的流程截图、我自己电脑里的 Codex
设置截图、之前手机和多设备的截图都串起来。你不需要一上来理解所有概念，先知道每个入口是干什么的，第一次任务怎么发，权限怎么开，结果怎么验收，就够了。

你先把这条链路跑通，比一上来研究所有高级功能更重要。

全文你可以按四层来看：

第一层，先把 Codex 是什么、主界面和权限看懂。

第二层，跑通第一条任务，学会写提示词、看 diff、跑测试。

第三层，再理解 Browser、Computer Use、Appshots、手机、多设备和 SSH。

第四层，最后再看 IDE、CLI、Cloud、AGENTS.md 和 7 天路线。

##  一、先把 Codex 想清楚

Codex 不是一个单独按钮。

它现在更像一套 AI 编程工作流，至少有四种常见入口：

  1. 1\. Codex App：适合管理任务、看进度、多设备、远程项目和一些本机操作。 
  2.   

  3. 2\. Codex Web / Cloud：适合让它在云端后台跑任务，尤其是 GitHub 仓库、PR、并行任务。 
  4.   

  5. 3\. Codex IDE Extension：适合在 VS Code、Cursor、Windsurf、JetBrains 这类编辑器里贴着代码现场干活。 
  6.   

  7. 4\. Codex CLI：适合在终端里使用，给它当前目录，让它读代码、改代码、跑命令。 

OpenAI 官方在 Codex 首页给的定位很直接：它是“everywhere you code”这一类 coding
agent。不是只能在一个地方用，而是尽量出现在你写代码、审代码、跑项目、看网页、接远程机器的地方。

![Codex 实操界面与结果](../图片素材/01-安装与首次使用/Codex保姆级入门-从安装权限到第一次让AI真正替你干活/02-Codex实操图-02.jpg)

我建议新手不要一上来纠结“到底用 App 还是 CLI”。

你先记一个简单分工：

  * • App：管任务。 
  * • IDE：看代码。 
  * • CLI：跑命令。 
  * • Browser：看网页效果。 
  * • Computer Use：操作桌面应用。 
  * • Cloud：后台跑长任务。 

这样理解以后，Codex 就不乱了。

很多工具乱，是因为它们只有一个入口，却想干所有事。Codex 现在的方向是反过来的：同一个 agent，进入不同工作现场。

以前 AI 是聊天窗口，现在是直接帮你拿结果。

##  二、新手先别急，先准备一个安全项目

很多兄弟第一次打开 Codex，最容易犯的错误是：直接拿自己最重要的项目试。

这个不建议。

不是因为 Codex 不行，而是因为你还不知道它会怎么读上下文、怎么跑命令、哪里需要你审批。

第一天最好拿一个安全项目。

比如：

  * • 一个 demo repo 
  * • 一个自己写着玩的脚本 
  * • 一个静态页面 
  * • 一个文档目录 
  * • 一个不涉及密钥、不涉及真实用户数据的小项目 

目标不是马上让 Codex 替你搞定生产问题。

目标是看懂 4 件事：

  1. 1\. 它怎么理解你的任务。 
  2. 2\. 它会改哪些文件。 
  3. 3\. 它会跑哪些命令。 
  4. 4\. 它最后怎么证明自己做完了。 

新手第一天把这 4 件事跑明白，后面就顺很多。

官方 Quickstart 里也把入口分成 App、IDE extension、CLI、Cloud
几类。你可以从任意入口开始，但如果你是第一次接触，我建议先用 Codex App，因为它能让你比较完整地看到任务、上下文、权限和执行过程。

![Codex 实操界面与结果](../图片素材/01-安装与首次使用/Codex保姆级入门-从安装权限到第一次让AI真正替你干活/03-Codex实操图-03.jpg)

注意看这张图。

新手最该先看的不是“怎么让它更强”，而是这些权限：

  * • 自动审核开不开。 
  * • 是否允许完全访问。 
  * • 什么时候需要你审批。 
  * • 当前工作空间是哪一个。 
  * • 它能不能操作本机。 

AI 编程真正进入下一阶段以后，权限会变成一个核心问题。

不给权限，AI 只能陪你聊天。

权限给太大，自己又不看 diff，就容易出问题。

正确做法不是一刀切，而是按任务给权限。

第一天就记一句话：

** 小任务、小权限、强验收。  **

随着你对 codex 能力边界熟悉了，就可以放开权限了，这样避免你每次确认浪费时间。

##  三、主界面怎么读

Codex 的主界面看着不复杂，但新手打开以后会懵。

因为你不知道到底该看哪里。

我按我的理解拆一下。

![Codex 实操界面与结果](../图片素材/01-安装与首次使用/Codex保姆级入门-从安装权限到第一次让AI真正替你干活/04-Codex实操图-04.jpg)

左侧主要是项目和历史任务。

你可以把它理解成“我现在让 Codex 管哪些工作空间”。这里会有不同项目，不同任务，也会保留一些历史对话。

中间是当前任务线程。

你发出去的任务、Codex 的思考和执行过程、它最后的结果，都会在这里展开。

右侧一般是环境信息。

比如当前 workspace、模型、执行环境、上下文状态、是否启用了某些能力。这里决定了 Codex 到底是在什么地方干活。

底部是输入区。

这个地方很关键。

![Codex 实操界面与结果](../图片素材/01-安装与首次使用/Codex保姆级入门-从安装权限到第一次让AI真正替你干活/05-Codex实操图-05.jpg)

你会看到模型、权限、发送按钮，以及当前任务能不能附加上下文。

我建议新手一开始不要写很长很散的提示词。

先按这个模板：

    背景：  
    这是一个什么项目，现在遇到什么问题。  
      
    目标：  
    我希望你完成什么。  
      
    范围：  
    可以改哪些文件，不能动哪些文件。  
      
    约束：  
    不要引入新依赖，不要改公开 API，不要改数据库结构。  
      
    验收：  
    完成后请告诉我改了哪些文件，并运行哪些测试或检查命令。

这个模版其实就是明确给 AI 一些方向，避免 AI 猜你的想法，总之越详细效果越好。

把 Codex 当成一个会犯错，但执行力很强的临时工程师。

随着你和 AI 互动沟通越多，后续AI 能给到你想要的答案，当然如果没有，还可以再发一条【内容】继续补充。

##  四、第一次任务怎么发

第一次任务不要大。

不要说：

    帮我优化一下这个项目。

这种任务太虚。

你可以说：

    请先阅读这个项目的 README、package.json 和主要入口文件。  
    只做分析，不改代码。  
    告诉我：  
    1. 这个项目是干什么的  
    2. 本地怎么启动  
    3. 测试命令是什么  
    4. 你建议我下一步让你做哪 3 个小任务

这个任务特别适合作为 Codex 的第一条任务。

原因很简单：它不改代码，但能让你看 Codex 怎么读项目。

第二条任务可以再小一点：

    请修复 README 里“本地启动步骤”不清楚的问题。  
    只改 README.md。  
    不要改代码。  
    改完后给我总结改动。

第三条任务再开始碰代码：

    请找到项目里负责登录页表单校验的代码。  
    只修复错误提示文案不统一的问题。  
    不要改接口逻辑。  
    改完后运行现有 lint 或测试。

这才是比较稳的入门方式。

![Codex 实操界面与结果](../图片素材/01-安装与首次使用/Codex保姆级入门-从安装权限到第一次让AI真正替你干活/06-Codex实操图-06.jpg)

官方视频里也能看到，Codex 的任务不是一次性问答，而是围绕一个 workspace 持续推进。

你可以补上下文，可以让它改，可以让它撤，可以让它解释。

这里有一个很重要的习惯：

不要只看最终答案。

你要看它中间做了什么。

比如它读了哪些文件，跑了哪些命令，为什么要改某个函数，测试失败以后怎么处理。

Codex 真正有价值的地方，不是最后那几行总结，而是它执行过程可追踪。

##  五、怎么写好任务提示词

很多人用 AI 编程效果不好，不是模型不行，而是任务写得太烂。

尤其是 Codex 这种能真的改项目的工具，提示词更像需求文档。

我给一个最常用的结构：

    你是这个项目里的临时工程师。  
      
    任务目标：  
    把用户设置页里的保存按钮，在请求中时显示 loading，并禁止重复点击。  
      
    上下文：  
    这个项目是 React + TypeScript。  
    设置页在 src/pages/settings 目录。  
    已有 Button 组件，优先复用，不要新造 UI 组件。  
      
    范围：  
    可以修改 settings 页面和相关 hook。  
    不要改接口层，不要改路由，不要改样式系统。  
      
    验收：  
    1. 保存中按钮显示 loading  
    2. 请求未结束前不能重复提交  
    3. 请求失败后恢复按钮状态  
    4. 运行 npm run lint  
    5. 最后说明改了哪些文件

你看，这里面没有玄学。

就是把“目标、上下文、范围、验收”讲清楚。

如果是修 bug，可以这样写：

    请排查这个 bug，但先不要直接改代码。  
      
    现象：  
    用户在移动端点击提交后，页面偶尔没有反馈。  
      
    我希望你先做：  
    1. 找到相关代码路径  
    2. 判断可能原因  
    3. 给出 2-3 个修复方案  
    4. 推荐最小改动方案  
      
    等我确认后再实施。

这类提示词很适合高风险场景。

你不是不让 Codex 干活，而是先让它出方案。

等你确认了，再让它动手。

这和带新人一样。

新人上来就乱改，你肯定不放心。先让他读代码、讲判断、列方案，你会放心很多。

##  六、做完以后，重点看 diff 和测试

Codex 做完，不代表你可以直接合并。

这个地方我说重一点。

新手一定要养成看 diff 的习惯。

AI 写代码最怕三件事：

  1. 1\. 看起来完成了，但边界没处理。 
  2. 2\. 改动范围扩大了，把不该动的地方也动了。 
  3. 3\. 测试没跑，或者跑失败了被忽略。 

所以每次完成后，你至少看 5 个东西：

    1. 改了哪些文件？  
    2. 有没有改到任务范围之外？  
    3. 有没有新增依赖？  
    4. 有没有跑 lint / test / build？  
    5. 有没有留下调试代码、假数据、敏感信息？

官方视频里有一个画面很典型，Codex 会给出自检和总结。

![Codex 实操界面与结果](../图片素材/01-安装与首次使用/Codex保姆级入门-从安装权限到第一次让AI真正替你干活/07-Codex实操图-07.jpg)

你可以继续追问：

    请按文件列出这次改动。  
    每个文件说明：  
    1. 为什么改  
    2. 具体改了什么  
    3. 有什么风险  
    4. 用什么命令验证过

如果它没有跑测试，你就直接问：

    你还没有运行测试。  
    请先根据项目文档找到测试命令。  
    如果没有测试命令，请说明你能运行的最小验证是什么。

这一步很重要。

不要因为 AI 很聪明，就把工程里的基本动作丢掉。

以前人写代码要 code review，现在 AI 写代码更要 review。

![Codex 实操界面与结果](../图片素材/01-安装与首次使用/Codex保姆级入门-从安装权限到第一次让AI真正替你干活/08-Codex实操图-08.jpg)

这里我自己的经验是：小任务可以快一点，大任务一定要慢一点。

比如改 README、修文案、补注释，风险很低，可以让它直接做。

但涉及支付、登录、权限、数据库迁移、用户数据、生产部署，一定要让它先出方案，再小步执行。

AI 编程不是把人拿掉。

AI 编程是把人从重复操作里解放出来，但最后判断还在人这里。

##  七、多任务是 Codex 的强项

我现在用 Codex 最爽的地方之一，是多任务。

不是一个任务结束再开下一个，而是几个互不影响的任务并行推进。

比如我可以同时让它做：

  * • 一个项目里修 README。 
  * • 另一个项目里跑测试失败分析。 
  * • 第三个项目里检查前端页面。 
  * • 第四个项目里整理 issue。 

当然，前提是任务之间别互相踩。

如果两个任务都在改同一批文件，就不适合并行。

![Codex 实操界面与结果](../图片素材/01-安装与首次使用/Codex保姆级入门-从安装权限到第一次让AI真正替你干活/09-Codex实操图-09.jpg)

多任务适合这几类：

  1. 1\. 文档类：补 README、生成变更说明、整理接口说明。 
  2. 2\. 检查类：跑 lint、跑测试、查失败日志、找潜在问题。 
  3. 3\. 小修类：文案统一、样式微调、删除无用代码。 
  4. 4\. 分析类：理解一个陌生模块、找入口、整理调用链。 

不适合这几类：

  1. 1\. 大规模架构重构。 
  2. 2\. 数据库迁移。 
  3. 3\. 支付和权限链路。 
  4. 4\. 多个任务同时改同一块核心代码。 

多任务的关键不是“开很多个”，而是“拆得足够独立”。

这和管理团队一样。

你不能让 5 个人同时改同一个函数，然后期待结果自动变好。

##  八、自动化任务怎么理解

Codex 还有 Automations。

这个我建议新手第二阶段再用。

先把普通任务、diff、测试跑明白，再玩自动化。

自动化适合什么？

适合那些“重复发生、规则清楚、结果可检查”的事情。

比如：

  * • 每天检查某个项目有没有 failing tests。 
  * • 每周整理一次依赖更新风险。 
  * • 定期扫描文档里过期链接。 
  * • 每天把某个仓库的 issue 分类。 
  * • 每周生成一次项目变更摘要。 

![Codex 实操界面与结果](../图片素材/01-安装与首次使用/Codex保姆级入门-从安装权限到第一次让AI真正替你干活/10-Codex实操图-10.jpg)

创建自动化时，最关键的是把任务写清楚。

不要写：

    每天帮我看看项目有没有问题。

这太虚。

改成：

    每天上午 10 点检查这个仓库：  
    1. 拉取最新主分支  
    2. 运行 npm run lint  
    3. 运行 npm test  
    4. 如果失败，汇总失败命令、错误摘要、疑似相关文件  
    5. 不要自动修改代码，只给报告

这个才叫自动化。

![Codex 实操界面与结果](../图片素材/01-安装与首次使用/Codex保姆级入门-从安装权限到第一次让AI真正替你干活/11-Codex实操图-11.jpg)

自动化里有一个坑：很多人喜欢让它“自动修”。

我建议刚开始只让它“自动查”和“自动报”。

等你确认它查得准，再逐步让它做低风险修复。

自动化像一个每天按时上班的助理，你得先给它 SOP。

我的习惯是你把自己跟 AI 的要求沉淀一个工作流，后续 AI
可以按照你的习惯执行，比如写完要测试，测试要注意到哪台服务器，测试完了要发正式等等，这样不容易跑偏。

##  九、Browser：前端任务一定要看页面

如果你用 Codex 做前端，千万不要只看代码。

前端最终是给人看的。

按钮有没有挤在一起，移动端有没有重叠，弹窗有没有遮住内容，颜色有没有看不清，这些问题不是只看 diff 能看出来的。

所以 Browser 很重要。

![Codex 实操界面与结果](../图片素材/01-安装与首次使用/Codex保姆级入门-从安装权限到第一次让AI真正替你干活/12-Codex实操图-12.jpg)

你可以让 Codex 打开本地页面，看截图，然后继续修。

比如：

    请启动项目并打开本地页面。  
    重点检查：  
    1. 375px 移动端是否有文字重叠  
    2. 1440px 桌面端首屏是否正常  
    3. 按钮文字是否溢出  
    4. 表单错误状态是否清楚  
      
    发现问题后先截图说明，再修改。

这类任务非常适合 Codex。

![Codex 实操界面与结果](../图片素材/01-安装与首次使用/Codex保姆级入门-从安装权限到第一次让AI真正替你干活/13-Codex实操图-13.jpg)

官方也有专门讲前端和 Codex 的视频。

前端工作流大概是：

    描述目标  
    → Codex 改代码  
    → Browser 打开页面  
    → 截图检查  
    → 继续修样式  
    → 再次验收

![Codex 实操界面与结果](../图片素材/01-安装与首次使用/Codex保姆级入门-从安装权限到第一次让AI真正替你干活/14-Codex实操图-14.jpg)

这里我建议你每次前端任务都加一句：

    改完后请用浏览器截图验证，不要只说代码已经改完。

这个要求很简单，但能过滤掉很多“代码看起来对，页面其实不对”的问题。

##  十、Computer Use：能用，但要慎重开

Computer Use 是让 Codex 操作你的电脑应用，比如浏览器、控制台、某些桌面软件。

我自己是很喜欢这个能力的，我最近填写云服务器配置，填写 app store 截图信息，做网页填表重复动作，都是靠他做。

有 Computer Use 之后，AI 可以进入 GUI 场景，彻底解放了我。

![Codex 实操界面与结果](../图片素材/01-安装与首次使用/Codex保姆级入门-从安装权限到第一次让AI真正替你干活/15-Codex实操图-15.jpg)

但我必须提醒一句：这个权限要慎重。

你不要让它碰这些东西：

  * • 支付确认 
  * • 转账 
  * • 删除数据 
  * • 账号安全设置 
  * • 密钥和 token 
  * • 私密聊天 
  * • 公司内部敏感系统 

如果必须让它进控制台，最好让它先说明计划：

    你将要操作浏览器控制台。  
    在点击任何提交、删除、支付、确认按钮前，必须停下来等我确认。  
    如果页面出现 token、密钥、手机号、邮箱，不要读取或复述。

这不是不信任 AI，这是基本安全边界。

你请一个真人助理操作电脑，也不会让他随便点支付按钮。

AI 也是一样，不过目前我感觉他的权限没有说，也会停下来等我确认这很好，但是最好给 AI 同步下要求。

##  十一、Appshots：把现场给 Codex 看

Appshots 可以理解成“把当前应用现场截图给 Codex”。

比如你现在正在一个报错页面，或者某个 App 的设置页，你想让 Codex 看当前状态，就可以用 Appshots。

![Codex 实操界面与结果](../图片素材/01-安装与首次使用/Codex保姆级入门-从安装权限到第一次让AI真正替你干活/16-Codex实操图-16.jpg)

这个能力适合这些场景：

  1. 1\. 页面报错，但你不想复制一堆文字。 
  2. 2\. 某个设置页你不知道怎么选。 
  3. 3\. 前端页面视觉有问题，需要 AI 看截图。 
  4. 4\. 你想让它基于当前界面继续解释下一步。 

但截图也有一个问题：很容易带敏感信息。

所以你要养成习惯：

  * • 截图前看一眼有没有邮箱、token、项目名。 
  * • 能打码就打码。 
  * • 不要把私密聊天、财务页面、后台用户数据直接丢进去。 

我这篇文章里自己的截图很多都是 codex 做的，他也都做了打码和标注。因为要公开发，就要多一道检查。

##  十二、手机、多设备和 SSH

我之前写过两篇 Codex App 的短文，一个讲手机控制，一个讲 Mac 控 Mac。

这次放到总教程里讲一下。

Codex 的连接能力有几个概念容易混：

第一种：让手机控制这台 Mac。

第二种：让这台 Mac 控制其他设备。

第三种：通过 SSH 连接远程项目。

它们不是一回事。

    桌面端开始设置  
    → 手机授权  
    → 桌面端确认允许  
    → 手机端选择项目发任务

![Codex 实操界面与结果](../图片素材/01-安装与首次使用/Codex保姆级入门-从安装权限到第一次让AI真正替你干活/18-Codex实操图-18.jpg)

如果你有多台 Mac，比如一台 MacBook、一台 Mac mini，就会用到“控制其他设备”。

![Codex 实操界面与结果](../图片素材/01-安装与首次使用/Codex保姆级入门-从安装权限到第一次让AI真正替你干活/19-Codex实操图-19.jpg)

这里最容易踩的坑是：被控那台 Mac 要先打开“允许其他设备连接”。

![Codex 实操界面与结果](../图片素材/01-安装与首次使用/Codex保姆级入门-从安装权限到第一次让AI真正替你干活/20-Codex实操图-20.jpg)

然后主控 Mac 才能添加设备。

![Codex 实操界面与结果](../图片素材/01-安装与首次使用/Codex保姆级入门-从安装权限到第一次让AI真正替你干活/21-Codex实操图-21.jpg)

添加后，你可以在新任务里选择远程项目。

![Codex 实操界面与结果](../图片素材/01-安装与首次使用/Codex保姆级入门-从安装权限到第一次让AI真正替你干活/22-Codex实操图-22.jpg)

如果是服务器、devbox、远程开发机，就看 SSH。

![Codex 实操界面与结果](../图片素材/01-安装与首次使用/Codex保姆级入门-从安装权限到第一次让AI真正替你干活/23-Codex实操图-23.jpg)

我对这块的理解是：

设备连接解决“哪台电脑干活”。

SSH 解决“哪个远程目录干活”。

手机解决“人不在电脑前怎么调度”。

这三个叠起来，Codex 才真正从“本机工具”变成“工作调度系统”，随时随地干活，coding，非常愉快。

IDE 入口最适合这几类任务：

  1. 1\. 解释当前文件。 
  2. 2\. 修改当前选中的代码。 
  3. 3\. 根据打开的代码做小范围重构。

IDE 和 App 的区别是什么？

我的理解：

App 更像任务中心。

IDE 更像手术台。

任务中心适合派活、看进度、切项目。

手术台适合盯着某个文件、某个 diff、某个函数细修。

你如果是程序员，我建议两边都用。

跨文件、跨项目、长任务放到 App 或 Cloud。

##  十四、CLI：终端党会很喜欢

Codex CLI 是在终端里跑的。

官方 CLI 文档里说，它可以在你选中的目录里读代码、改代码、运行代码，而且是开源的。

![Codex 实操界面与结果](../图片素材/01-安装与首次使用/Codex保姆级入门-从安装权限到第一次让AI真正替你干活/28-Codex实操图-28.jpg)

CLI 适合这些人：

  * • 习惯终端工作的人。 
  * • 经常写脚本的人。 
  * • 想把 Codex 放进现有命令行工作流的人。 
  * • 不想一直打开图形界面的人。 

常见用法就是进入项目目录，然后运行 Codex。

    cd your-project  
    codex

然后你可以在 TUI 里继续对话，让它看当前目录、改文件、跑命令。

如果你还不熟 CLI，不建议第一天从这里开始。

App 更直观。

但等你用熟以后，CLI 会很爽。

因为它离真实工程环境很近。

![Codex 实操界面与结果](../图片素材/01-安装与首次使用/Codex保姆级入门-从安装权限到第一次让AI真正替你干活/29-Codex实操图-29.jpg)

我建议大家至少理解 CLI。

哪怕你平时主要用 App，也要知道 Codex 不是只能在图形界面里工作，而可以再其他维度使用。

##  十五、Code Review：新手很适合从这里入门

很多人第一次用 AI 改代码会紧张。

那你可以先不让它改。

让它 review。

Code Review 是我很推荐的新手入口。

因为 review 的风险比直接改低，但能让你看到 Codex 的判断力。

![Codex 实操界面与结果](../图片素材/01-安装与首次使用/Codex保姆级入门-从安装权限到第一次让AI真正替你干活/30-Codex实操图-30.jpg)

你可以让它看一个 PR：

    请 review 这个改动。  
      
    重点看：  
    1. 有没有明显 bug  
    2. 有没有边界条件没处理  
    3. 有没有安全风险  
    4. 有没有测试缺口  
    5. 有没有可以简化的地方  
      
    只给 review 意见，不要直接改代码。

也可以让它看本地 diff：

    请 review 当前 git diff。  
    按严重程度输出：  
    P0 必须修  
    P1 建议修  
    P2 可以优化  
      
    不要泛泛而谈，每个问题都指出文件和原因。

![Codex 实操界面与结果](../图片素材/01-安装与首次使用/Codex保姆级入门-从安装权限到第一次让AI真正替你干活/31-Codex实操图-31.jpg)

这个场景很适合建立信任。

它指出的问题如果靠谱，你就知道它对项目有理解。

它指出的问题如果不靠谱，你也能看出来它在哪些地方会误判。

比起让它一上来改核心逻辑，先让它 review，是一个更稳的方式。

##  十六、Cloud：适合后台长任务

Codex Web / Cloud 适合让它在后台做事。

官方文档里强调，Codex cloud 可以在自己的云端环境里后台跑任务，包括并行任务。你连接 GitHub 以后，它可以基于仓库工作，并产出 PR。

![Codex 实操界面与结果](../图片素材/01-安装与首次使用/Codex保姆级入门-从安装权限到第一次让AI真正替你干活/32-Codex实操图-32.jpg)

Cloud 适合这些任务：

  * • 修一个独立 issue。 
  * • 给一个 PR 补测试。 
  * • 更新文档。 
  * • 检查一批失败用例。 
  * • 做一次小范围重构。 

Cloud 不适合什么？

  * • 需要频繁看本地 UI 的前端细节。 
  * • 需要你本机私有环境的操作。 
  * • 需要手动登录复杂后台。 
  * • 依赖你本机很多未提交文件的任务。 

我的建议是：

    本地强依赖，用 App / IDE / CLI。  
    仓库型后台任务，用 Cloud。  
    网页视觉验收，用 Browser。  
    桌面操作，用 Computer Use。

不要把所有事都塞给一个入口。

入口选对，体验会好很多。

##  十七、AGENTS.md：让 Codex 懂你的项目规矩

新手用 Codex 经常忽略一个点：上下文不是只靠聊天里说。

项目里应该有自己的规则。

比如：

  * • 项目怎么启动。 
  * • 测试命令是什么。 
  * • 代码风格是什么。 
  * • 哪些目录不能改。 
  * • 发布流程是什么。 
  * • 重要业务边界是什么。 

这些东西如果每次都靠你手写，非常累。

所以应该沉淀到项目文档里。

最简单就是 README。

更进一步，可以写 AGENTS.md。

你可以放类似内容：

    # AGENTS.md  
      
    ## 项目说明  
      
    这是一个 Next.js 项目，使用 pnpm。  
      
    ## 常用命令  
      
    - 安装依赖：pnpm install  
    - 本地开发：pnpm dev  
    - Lint：pnpm lint  
    - 测试：pnpm test  
    - 构建：pnpm build  
      
    ## 修改规则  
      
    - 不要改数据库 schema，除非用户明确要求。  
    - 不要新增依赖，除非说明理由。  
    - 修改前先读 README 和 package.json。  
    - 完成后必须说明改了哪些文件，以及跑了哪些命令。

这类文件本质上是给 AI 的项目 SOP。

你越常用 Codex，越会发现：真正提升效率的不是每次写一个很长 prompt，而是把项目规则沉淀下来。

这和我现在维护 Obsidian 知识库的逻辑一样。

不是让 AI 每次从 0 理解我，而是把长期上下文放在固定地方。

这也是我现在越来越重视  AGENTS.md  的原因。

工具用久以后，真正拉开差距的不是某一次 prompt 写得多漂亮，而是你的项目有没有沉淀出一套稳定规矩。

##  十八、非工程角色怎么用 Codex

Codex 不只是程序员工具。

PM、设计师、运营也能用。

但用法不一样。

PM 不一定要让 Codex 写代码，可以让它理解需求、拆验收标准、看实现有没有漏。

比如：

    请阅读这个 PR 和需求描述。  
    从产品经理视角检查：  
    1. 是否覆盖需求里的每个验收点  
    2. 是否有明显边界漏掉  
    3. 是否需要补充空状态、错误状态、加载状态  
    4. 是否有用户体验风险  
      
    不要改代码，只给检查清单。

官方 PM 视频里也有类似思路：用自然语言把产品问题交给 Codex，让它结合项目上下文分析。

![Codex 实操界面与结果](../图片素材/01-安装与首次使用/Codex保姆级入门-从安装权限到第一次让AI真正替你干活/33-Codex实操图-33.jpg)

设计师也一样。

不是让 Codex 替代设计，而是把设计稿、原型、已有页面串起来，让它做可运行的东西。

![Codex 实操界面与结果](../图片素材/01-安装与首次使用/Codex保姆级入门-从安装权限到第一次让AI真正替你干活/34-Codex实操图-34.jpg)

运营和内容同学也可以用它做脚本、批处理、数据整理、页面检查。

但有一个前提：你要把任务说清楚。

不会写代码没关系。

不会描述目标，才是问题。

##  十九、新手最容易踩的 12 个坑

我直接列，兄弟们对照避坑。

###  1\. 一上来就让它做大项目

比如“帮我重构整个系统”。

这个任务太大，失败概率很高。

先拆成：

    先读项目并给重构建议，不改代码。

###  2\. 不给验收条件

你不告诉它怎么算完成，它只能自己猜。

一定要写测试、lint、截图、文件范围。

###  3\. 不看 diff

这个最危险。

AI 改完代码，你至少要看一眼改了哪些文件。

###  4\. 直接在生产项目里开大权限

第一天不要这么玩。

先 demo 项目，后真实项目。

###  5\. 同时开多个任务改同一批文件

这会互相覆盖。

多任务要拆独立。

###  6\. 把 Codex 当搜索引擎

Codex 的价值不是搜答案，而是在项目上下文里执行。

问概念可以用 ChatGPT。

改项目、跑验证、看 diff，才是 Codex 的主场。

###  7\. 不沉淀项目规则

每次都重新解释项目，效率很低。

README、AGENTS.md、测试命令，都要沉淀。

###  8\. 让它操作敏感后台

Computer Use 很强，但敏感后台要谨慎。

支付、删除、账号安全、密钥，一律人工确认。

###  9\. 前端任务不看截图

前端一定要让它打开浏览器验收。

只说 build 通过不够。

###  10\. 让它自动化模糊任务

自动化必须有明确 SOP。

不然每天都会产出一堆没法用的报告。

###  11\. 不区分 App、IDE、CLI、Cloud

入口选错，体验会差。

任务中心用 App，代码现场用 IDE，终端流程用 CLI，后台仓库任务用 Cloud。建议多用 codex app

###  12\. 期待一次提示词解决所有问题

真正的工作流是多轮。

读代码，出方案，改一小步，跑验证，再继续。

不要幻想一条 prompt 直接变成完美工程。

##  二十、我建议的新手 7 天路线

如果你现在从 0 开始，我建议按 7 天来。

###  第 1 天：只读项目，不改代码

任务：

    请阅读这个项目，告诉我项目结构、本地启动方式、测试命令和你建议的 3 个小任务。

目标：看懂 Codex 怎么读上下文。

###  第 2 天：只改文档

任务：

    请根据项目实际结构，补充 README 的本地启动说明。  
    只改 README。

目标：看懂它怎么改文件。

###  第 3 天：修一个低风险 bug

任务：

    请修复某个按钮文案不一致的问题。  
    不要改接口逻辑。  
    改完跑 lint。

目标：看 diff 和验证。

###  第 4 天：让它做 code review

任务：

    请 review 当前 diff，只给意见，不改代码。

目标：训练你判断它的质量。

###  第 5 天：做一次前端浏览器验收

任务：

    请启动本地项目，用浏览器检查移动端和桌面端首屏。  
    发现问题先截图说明，再改。

目标：把代码和视觉结果接起来。

###  第 6 天：尝试 IDE 或 CLI

如果你是程序员，开始把 Codex 放到 IDE 或终端里。

目标：让它贴近你真实写代码的地方。

###  第 7 天：写 AGENTS.md

把项目规则沉淀下来。

目标：让下次任务不再从 0 开始。

这 7 天跑完，你基本就不是“试用一下 Codex”了。

你已经开始建立 AI 编程工作流。

##  二十一、我的最终建议

我现在越来越确定一件事：

AI 编程不是单个工具竞争，而是工作流竞争。

谁能进入真实项目，谁能读上下文，谁能跑验证，谁能跨设备，谁能接浏览器、终端、IDE、远程机器，谁才有机会真正改变开发方式。

Codex 现在让我感兴趣的地方就在这里。

它不是只在聊天框里回答你，而是直接帮你拿结果，这个最重要。

这也是我说他比小龙虾 open claw 和 hermes agent 更方便了。

![Codex 实操界面与结果](../图片素材/01-安装与首次使用/Codex保姆级入门-从安装权限到第一次让AI真正替你干活/35-Codex实操图-35.jpg)

但新手一定要记住：

不要神化它，也不要因为怕出错就不用。

先从一个 demo 项目开始，干起来。

说到底，工具不是拿来供着的，是拿来干活的。
